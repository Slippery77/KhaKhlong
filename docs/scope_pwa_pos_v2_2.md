# 3.2 ขอบเขตการทำงานของระบบ (Scope)
**PWA-POS: ระบบจุดขายสำหรับธุรกิจร้านอาหารขนาดเล็ก**

> เอกสารนี้เป็นสรุปขอบเขตระดับ Requirement/Business Rule สำหรับใช้เขียน Proposal
> **ยังไม่ใช่ Feature Specification / API Contract ที่พร้อมให้ทีมเริ่มพัฒนา Frontend**
> ต้องผ่านขั้นตอนออกแบบ API Design และ UI/UX Flow ก่อนเริ่มพัฒนาจริงในแต่ละโมดูล
>
> **หมายเหตุการแก้ไขล่าสุด:** อัปเดตหัวข้อ 3.2.2 (Table Management) เพิ่มรายละเอียด `table_number`, `capacity`, `floor` ให้ตรงกับ Business Rules ข้อ TBL-08/TBL-09/TBL-10 — ยืนยันชัดเจนว่าระบบรองรับการแบ่ง "ชั้น" แต่ไม่รองรับการแบ่ง "โซน" ในเวอร์ชันนี้
> **หมายเหตุการแก้ไขล่าสุด (รอบ 2):** อัปเดตหัวข้อ 3.2.3 (Menu Management) เพิ่มรายละเอียดกติกาการเลือก Modifier Group (Single/Multi Select, Required/Optional) ให้ตรงกับ Business Rules ข้อ MOD-08
> **หมายเหตุการแก้ไขล่าสุด (รอบ 3):** เปลี่ยนสถาปัตยกรรมหัวข้อ 3.2.5 (Inventory Management) จาก Recipe-based Real-time Deduction เป็น **Periodic Physical Count** ตามการตัดสินใจร่วมกับอาจารย์ที่ปรึกษา — ดูเหตุผลเต็มที่ `business-rules-pos-updated.md` ข้อ `INV-11` แก้ไขหัวข้อ 3.2.11 (Offline) ตัด Open Item เรื่อง Offline Inventory Conflict ออก
>
> **หมายเหตุการแก้ไขล่าสุด (รอบ 4 — 2 ตุลาคม 2569):** ปรับเอกสารให้ตรงกับฐานข้อมูลที่ติดตั้งและทดสอบจริงแล้ว (`FULL_INSTALL.sql`) โดยแก้ไข 8 จุด
> 1. **จำนวนตาราง** จาก 23 เป็น **28 ตาราง และ 3 View** (ตัวเลข 23 เป็นการนับก่อนออกแบบรอบสุดท้าย ซึ่งยังไม่มีตาราง `config_definitions`, `refresh_tokens`, `receipt_sequences`, `order_sequences`, `cash_movements` และตารางย่อยของการชำระเงิน)
> 2. **สถานะ ERD** จาก "ยังอยู่ระหว่างการออกแบบ ยังไม่เคยถูก Execute" เป็น **ติดตั้งและทดสอบแล้วบน PostgreSQL 16.13**
> 3. **หัวข้อ 3.2.1** เงื่อนไข "ต้องเสิร์ฟครบก่อนชำระ" เปลี่ยนจากกฎตายตัวเป็น Configuration และเพิ่มรายละเอียดโหมดภาษีมูลค่าเพิ่ม 3 โหมด
> 4. **หัวข้อ 3.2.4** เพิ่มสถานะรายการอาหารบนจอครัวทั้ง 5 สถานะ
> 5. **หัวข้อ 3.2.5** แก้ชื่อประเภทรายการจาก `purchase` เป็น `restock` ให้ตรงกับฐานข้อมูล
> 6. **หัวข้อ 3.2.7** เพิ่มรายละเอียดกลไก Configuration ที่มี 9 รายการและมีตารางนิยามกำกับ
> 7. **หัวข้อ 3.2.10** เพิ่มการเปิดกะใหม่ (Reopen) และการบันทึกเงินเข้า-ออกลิ้นชัก
> 8. **หัวข้อ 3.3** แก้เหตุผลที่ไม่ทำ Split Bill ให้เป็นเหตุผลเชิงโครงสร้างตามความจริง และปรับรายการใบกำกับภาษีให้ตรงกับสิ่งที่ระบบรองรับจริง

## 3.2.1 ระบบการขาย (Sales / Order Management)

- สามารถเพิ่ม ลด ยกเลิก รายการอาหารในออเดอร์
- สามารถค้นหาเมนูด้วยชื่อหรือรหัสอาหาร
- สามารถพักออเดอร์ของโต๊ะหนึ่งไว้ชั่วคราว เพื่อสลับไปทำรายการของโต๊ะอื่นได้ (ยังไม่เกี่ยวข้องกับขั้นตอนชำระเงิน)
- แต่ละใบสั่งอาหารมี **เลขที่ใบสั่งอาหาร (`order_number`)** ที่รันใหม่ทุกวันทำการ สำหรับให้พนักงานเรียกสื่อสารกันหน้างาน แยกจากรหัสภายในที่เป็น UUID
- สามารถรวมยอดชำระเงินจากหลายโต๊ะเข้าเป็นบิลเดียวได้ในขั้นตอนการชำระเงิน (**รวมบิล / Bill Merge**)
  - แต่ละโต๊ะยังคงมีรายการออเดอร์แยกกันตามปกติในระบบ
  - การรวมยอดเกิดขึ้น ณ ขั้นตอนสร้างรายการชำระเงิน (Payment) เท่านั้น ไม่กระทบความสัมพันธ์ระหว่าง Order และ Table
  - เมื่อชำระเงินสำเร็จ ทุกโต๊ะที่ถูกรวมจะถูกปิดและเปลี่ยนสถานะเป็น "ว่าง" พร้อมกัน
  - **เงื่อนไขก่อนรวมบิล/ชำระเงินได้:** ค่าเริ่มต้นคือรายการอาหารทุกรายการ ในทุกโต๊ะที่ถูกรวม ต้องมีสถานะ "เสิร์ฟแล้ว" ครบถ้วน เพื่อป้องกันกรณีจ่ายเงินไปแล้วแต่อาหารยังมาไม่ครบ — **[แก้ไขรอบ 4]** เงื่อนไขนี้เปลี่ยนเป็น Configuration ชื่อ `require_all_served_before_payment` ที่ปิดได้ เนื่องจากร้านที่ให้ลูกค้าจ่ายเงินก่อนรับอาหาร (ร้านข้าวแกง ศูนย์อาหาร) จะใช้ระบบไม่ได้เลยหากบังคับเป็นกฎตายตัว
- **การคำนวณภาษีมูลค่าเพิ่ม** รองรับ 3 โหมดผ่านระบบตั้งค่า โดยค่าเริ่มต้นคือ **ไม่คิดภาษี** เพราะร้านอาหารขนาดเล็กจำนวนมากไม่ได้จดทะเบียนภาษีมูลค่าเพิ่ม

  | โหมด | ความหมาย | เมนูราคา 60 บาท ลูกค้าจ่าย |
  |---|---|---|
  | `none` | ไม่จดทะเบียนภาษีมูลค่าเพิ่ม (ค่าเริ่มต้น) | 60.00 |
  | `inclusive` | ราคาเมนูรวมภาษีแล้ว | 60.00 |
  | `exclusive` | บวกภาษีเพิ่มจากราคา | 64.20 |

  การเปลี่ยนออกจากโหมด `none` ถูกบังคับให้ต้องกรอกเลขประจำตัวผู้เสียภาษีของร้านก่อน และทุกรายการชำระเงินเก็บโหมดกับอัตราภาษี ณ เวลานั้นไว้ในแถวของตนเอง ทำให้พิมพ์เอกสารย้อนหลังได้ถูกต้องแม้อัตราจะเปลี่ยนไปแล้ว
- สามารถคำนวณเงินทอนได้ถูกต้อง
- สามารถเลือกรูปแบบการชำระเงิน เช่น เงินสด หรือ QR Code
- **ปิดบิลโดยไม่เก็บเงินได้** ในกรณีที่ลูกค้าเดินออกไปโดยไม่สั่ง ลูกค้าไม่ชำระเงิน หรือรายการถูกยกเลิกทั้งหมด โดยต้องมีสิทธิ์ `order:close_unpaid` และบันทึกผู้ปิดกับเหตุผลไว้ เพื่อให้โต๊ะกลับมาว่างได้โดยไม่ต้องสร้างรายการชำระเงินปลอม

## 3.2.2 ระบบจัดการโต๊ะ (Table Management)

- สามารถเปิด/ปิดโต๊ะเพื่อเริ่ม-จบการให้บริการ
- สามารถย้ายโต๊ะ (Move Table)
- สามารถแสดงสถานะโต๊ะ (ว่าง / มีลูกค้า)
- แต่ละโต๊ะมีหมายเลข/ชื่อโต๊ะ (`table_number`) และจำนวนที่นั่งสูงสุด (`capacity`) แสดงให้พนักงานเห็นประกอบการตัดสินใจตอนจัดโต๊ะ/ย้ายโต๊ะ — ระบบ**ไม่บังคับ**ว่าจำนวนลูกค้าต้องไม่เกิน capacity (เป็นข้อมูลอ้างอิง ไม่ใช่ Validation Rule)
- รองรับร้านที่มีอาคารมากกว่า 1 ชั้น โดยแต่ละโต๊ะระบุ "ชั้น" (`floor`) ที่ตั้งอยู่ได้ ใช้สำหรับ Filter/Group การแสดงผลบนหน้าจอเท่านั้น ไม่มี Business Logic อื่นผูกกับค่านี้
  - **ขอบเขตที่จำกัดไว้โดยตั้งใจ:** ระบบรองรับเฉพาะการแบ่ง "ชั้น" (Physical Fact ของอาคาร) เท่านั้น **ไม่รองรับ** การแบ่ง "โซน" (เช่น โซนสูบบุหรี่, โซน VIP, ผังโต๊ะแบบ Drag-and-Drop) ในเวอร์ชันนี้ เนื่องจากกลุ่มเป้าหมาย (ร้านอาหารขนาดเล็ก) ไม่มี Use Case ที่จำเป็นต้องใช้ และการรองรับโซนจะเพิ่ม CRUD/Edge Case ที่ไม่คุ้มกับคุณค่าที่ได้ (ยึดหลักการ YAGNI เดียวกับที่ใช้กำหนดขอบเขต Role และหมวดหมู่เมนู)
  - เลขโต๊ะ (`table_number`) ต้องไม่ซ้ำกันภายในร้านเดียวกัน **รวมถึงข้ามชั้นด้วย** (ไม่อนุญาตให้ชั้น 1 และชั้น 2 มีโต๊ะ "A1" ซ้ำกัน) เพื่อลดความสับสนตอนเรียกชื่อโต๊ะหน้าร้าน
  - **[แก้ไขรอบ 4]** ฐานข้อมูลบังคับไว้ด้วยว่า **หนึ่งโต๊ะมีใบสั่งอาหารที่ยังไม่ปิดได้ไม่เกินหนึ่งใบ** ป้องกันกรณีพนักงานสองคนกดเปิดโต๊ะเดียวกันพร้อมกันจากสองเครื่องแล้วได้บิลซ้อนกันสองใบ

## 3.2.3 ระบบจัดการเมนู (Menu Management)

- สามารถเพิ่ม/แก้ไข/ลบรายการอาหาร
- สามารถจัดหมวดหมู่เมนู (แบบชั้นเดียว ไม่มีหมวดหมู่ย่อยซ้อนกัน)
- สามารถกำหนดราคาและสถานะพร้อมจำหน่าย/ไม่พร้อมจำหน่าย — เมนูที่ตั้งเป็นไม่พร้อมจำหน่ายจะสั่งไม่ได้ โดยบังคับที่ระดับฐานข้อมูล ไม่ใช่แค่ซ่อนปุ่มบนหน้าจอ
- **ระบบ Add-on / Modifier** — รองรับตัวเลือกเพิ่มเติมของเมนู 2 รูปแบบ:
  - Free-text (คำขอพิเศษที่ไม่กระทบราคา/สต็อก เช่น "ไม่ใส่ผัก")
  - Structured Modifier (ตัวเลือกที่มีผลต่อราคา เช่น "เพิ่มไข่ดาว") ใช้ร่วมกันได้หลายเมนูผ่าน Modifier Group
- Modifier Group แต่ละกลุ่มกำหนดกติกาการเลือกได้ 2 มิติ: **เลือกได้กี่ตัว** (เลือกได้ตัวเดียว เช่น ระดับความเผ็ด/ขนาดแก้ว หรือเลือกได้หลายตัว เช่น Topping เพิ่มเติม) และ **บังคับเลือกหรือไม่** (เช่น ต้องเลือกขนาดแก้วก่อนสั่งได้ ในขณะที่ Topping เป็นตัวเลือกเสริมที่ไม่บังคับ) — ระบบยังไม่รองรับการกำหนดจำนวนขั้นต่ำ/สูงสุดแบบละเอียด (เช่น "เลือก 2-3 ตัว") ในเวอร์ชันนี้
- **[แก้ไขรอบ 4]** กฎ "บังคับเลือก" บังคับใช้ที่ฝั่ง Frontend เท่านั้น เนื่องจาก Modifier ถูกบันทึกลงฐานข้อมูลหลังรายการสั่งอาหาร ฐานข้อมูลจึงยังไม่ทราบว่าผู้ใช้เลือกครบหรือยัง ณ เวลาที่บันทึกรายการ
- ราคาเมนูถูกคัดลอกเก็บไว้ในรายการสั่งอาหารทุกครั้ง (Price Snapshot) การแก้ราคาเมนูภายหลังจึงไม่กระทบบิลที่ขายไปแล้ว

## 3.2.4 ระบบครัว (Kitchen Display System)

- แสดงคิวออเดอร์ที่ส่งเข้าครัว เรียงตามเวลาที่ส่งเข้าคิว
- **[แก้ไขรอบ 4]** ติดตามสถานะรายการอาหารครบทั้ง 5 สถานะ ได้แก่ `queued` (เข้าคิว) · `preparing` (กำลังทำ) · `ready` (พร้อมเสิร์ฟ) · `served` (เสิร์ฟแล้ว) · `voided` (ยกเลิก) โดยเปลี่ยนสถานะย้อนกลับไม่ได้ และเปลี่ยนข้ามขั้นไม่ได้
- รายการที่ถูกส่งเข้าครัวในการกดครั้งเดียวกันจะมี `kitchen_ticket_id` ค่าเดียวกัน เพื่อให้ครัวเห็นว่าชุดไหนมาพร้อมกัน
- **การยกเลิกรายการ** ทำได้ทั้งขณะ `queued` และขณะ `preparing` โดยการยกเลิกขณะครัวกำลังทำต้องมีสิทธิ์ `void:approve` และระบุเหตุผล ส่วนรายการที่เสิร์ฟไปแล้วใช้กลไก Comp แทน (ปรับราคาเป็น 0 ไม่ใช่ลบรายการ)
- **[แก้ไขรอบ 4]** การดึงคิวขึ้นจอใช้ Partial Index ที่ครอบเฉพาะสถานะที่ยังค้างอยู่ ทำให้เวลาในการดึงข้อมูลไม่เพิ่มขึ้นตามประวัติการขายที่สะสม วัดได้ 0.27 มิลลิวินาที บนข้อมูลรายการอาหาร 28,800 รายการ

## 3.2.5 ระบบสต็อกวัตถุดิบ (Inventory Management)

> **[แก้ไขรอบ 3]** เปลี่ยนจากแนวทาง Recipe-based Deduction เป็น **Periodic Physical Count** — ดูเหตุผลที่ `business-rules-pos-updated.md` ข้อ `INV-11`

- สามารถเพิ่ม/แก้ไข/ลบวัตถุดิบ
- **[แก้ไขรอบ 4]** บันทึกความเคลื่อนไหวของวัตถุดิบได้ 3 ประเภท คือ `restock` (รับของเข้า/ซื้อมาเติม) · `waste` (ของเสีย/หมดอายุ) · `adjustment` (ผลต่างจากการนับจริง) — ชื่อ `purchase` ในเอกสารรอบก่อนถูกรวมเข้ากับ `restock` เพราะสื่อความหมายเดียวกัน
- **สามารถบันทึกยอดวัตถุดิบคงเหลือแบบนับจริงประจำวัน (Periodic Physical Count):** พนักงาน/Manager ชั่งน้ำหนัก(หรือนับ)วัตถุดิบที่เหลือจริงตอนจบวัน/จบรอบ แล้วกรอกยอดเข้าระบบ ระบบคำนวณผลต่าง (Delta) จากยอดที่คำนวณสะสมไว้ให้อัตโนมัติ และบันทึกเป็นรายการประเภท `adjustment`
- **[แก้ไขรอบ 4]** หากผลต่างจากการนับเกินเกณฑ์ที่ร้านตั้งไว้ (ค่าเริ่มต้น 20% และต้องเกิน 1 หน่วยด้วย) ระบบเขียนบันทึกลง Audit Log อัตโนมัติ เพื่อให้เจ้าของร้านตรวจย้อนหลังได้ว่าวัตถุดิบตัวไหนหายผิดปกติ
- ความเคลื่อนไหวของวัตถุดิบทุกรายการ **แก้ไขและลบไม่ได้** เมื่อบันทึกแล้ว หากกรอกผิดต้องบันทึกรายการแก้ไขใหม่ทับ เพื่อให้ยอดคงเหลือตรวจสอบย้อนหลังได้ทุกบรรทัด
- แจ้งเตือนเมื่อสต็อกตํ่ากว่าที่กำหนด (Query-time Badge บนหน้าจอ — อ้างอิงจากยอดที่คำนวณจากการนับล่าสุด ไม่ใช่ Real-time เป๊ะ)
- **ไม่มี**การผูกวัตถุดิบกับเมนูอาหาร (Recipe) และ**ไม่มี**การตัดสต็อกอัตโนมัติตอนสั่งอาหาร — เป็นการตัดสินใจโดยเจตนา (Trade-off) เพราะพ่อครัว/พนักงานร้านอาหารขนาดเล็กไม่มีเวลาตวงวัตถุดิบทุกจานในช่วงเวลาเร่งด่วนจริง กลไก Recipe-level Deduction แม่นยำเฉพาะร้านที่มี Central Kitchen พรีพอร์ชั่นมาก่อนเท่านั้น ซึ่งไม่ตรงกับกลุ่มเป้าหมายของโครงงานนี้ — ผลคือระบบไม่สามารถ Block การขายอัตโนมัติเมื่อวัตถุดิบหมด ต้องพึ่งพนักงานปิดเมนูเอง (Manual Toggle)

## 3.2.6 ระบบผู้ใช้งาน (User Management)

- สามารถเข้าสู่ระบบและออกจากระบบ
- สามารถกำหนดสิทธิ์การใช้งานตามบทบาท (Role-Based Access Control) โดยมี 3 บทบาท คือ Owner, Manager, Employee และมีสิทธิ์ย่อยรวม 25 รายการ — ดูตารางสิทธิ์เต็มที่ `user-roles-permissions.md`
- **[แก้ไขรอบ 4]** สิทธิ์ที่เกี่ยวกับเงินและการอนุมัติถูกตรวจซ้ำที่ระดับฐานข้อมูลด้วย ไม่ใช่ตรวจเฉพาะที่ Guard ฝั่ง API เพื่อให้แม้มีช่องโหว่ที่ API ก็ยังไม่สามารถยกเว้นค่าอาหารหรือยกเลิกรายการที่ครัวกำลังทำได้โดยไม่มีสิทธิ์
- รองรับการเข้าสู่ระบบด้วยรหัส PIN สำหรับการใช้งานหน้าร้านที่ต้องสลับผู้ใช้บ่อย พร้อมกลไกนับจำนวนครั้งที่กรอกผิดและล็อกบัญชีชั่วคราว
- **บันทึกประวัติการใช้งานสำคัญ (Audit Log)** ครอบคลุมทั้งการกระทำที่มีตารางบันทึกของตัวเองอยู่แล้ว (เช่น การชำระเงิน, การเคลื่อนไหวสต็อก, การ Void/Comp, การพิมพ์ใบเสร็จซ้ำ) และการกระทำที่ไม่มีตารางรองรับโดยตรง ซึ่งบันทึกลง Audit Log โดยเฉพาะ ได้แก่ การเข้า/ออกระบบ (สำเร็จและล้มเหลว), การแก้ไขราคาเมนู, การเปลี่ยนบทบาทผู้ใช้งาน, การเปลี่ยนสถานะโต๊ะ, การเปิดกะที่ปิดแล้วใหม่ และการแก้ไขค่าตั้งค่าระบบ รวม **17 ประเภทเหตุการณ์** — สิทธิ์เข้าถึงหน้า Audit Log จำกัดเฉพาะ Owner และ Manager
- บันทึก Audit Log ลบไม่ได้ ยกเว้นการลบตามรอบอายุข้อมูลที่เกิน 1 ปี ผ่านฟังก์ชันที่ระบบเตรียมไว้

## 3.2.7 ระบบตั้งค่าระบบ (System Configuration)

- สามารถตั้งค่าข้อมูลร้านค้า (ชื่อร้าน ที่อยู่ เลขประจำตัวผู้เสียภาษี)
- สามารถกำหนดและปรับเปลี่ยนอัตราภาษีมูลค่าเพิ่มและค่าบริการ (Service Charge)
- **[แก้ไขรอบ 4]** ค่าตั้งค่าทั้งหมดมี **9 รายการ** และทุกรายการมีตารางนิยามกำกับไว้ว่าเป็นข้อมูลชนิดใด รับค่าในช่วงใด และบทบาทใดแก้ได้ ทำให้ใส่ค่านอกขอบเขตหรือพิมพ์ชื่อค่าผิดไม่ได้ ร้านที่สมัครใหม่จะได้ค่าตั้งต้นครบทุกรายการอัตโนมัติ
- ค่าตั้งค่าแบ่งเป็น 2 ระดับ คือค่าที่กระทบเงินและเอกสารภาษี (แก้ได้เฉพาะ Owner) และค่าเชิงปฏิบัติงาน เช่น การเปิดจอครัว จำนวนครั้งที่พิมพ์ใบเสร็จซ้ำได้ ชั่วโมงเริ่มวันทำการ (Manager แก้ได้)
- **หลักการที่ยึดถือ** ทุกค่าตั้งค่าต้องมีส่วนของระบบที่อ่านค่านั้นไปใช้จริง ค่าที่ไม่มีใครอ่านจะถูกลบออก ไม่เก็บไว้เป็นตัวเลือกหลอกผู้ใช้ — ดูกฎ `CFG-09` ใน `business-rules-pos-updated.md`

## 3.2.9 ระบบใบเสร็จ (Receipt System)

- สามารถออกใบเสร็จในรูปแบบดิจิทัล (PDF)
- สามารถแสดงประวัติใบเสร็จย้อนหลัง
- **[แก้ไขรอบ 4]** เลขที่ใบเสร็จรันต่อเนื่องแยกตามร้านและวันทำการ โดยใช้กลไกตัวนับที่ทดสอบแล้วว่าไม่ซ้ำและไม่ข้ามเลขแม้มีการชำระเงินพร้อมกันหลายเครื่อง
- การพิมพ์ใบเสร็จซ้ำถูกบันทึกทุกครั้งว่าใครพิมพ์เมื่อใด และจำกัดจำนวนครั้งได้ตามค่าที่ร้านตั้งไว้ เพื่อป้องกันการพิมพ์ใบเสร็จหลายใบจากบิลเดียวไปใช้ในทางที่ผิด
- ใบเสร็จรวมรายการที่เหมือนกันเป็นบรรทัดเดียวอัตโนมัติ โดยจัดกลุ่มตามราคาและชุด Modifier ทำให้จานที่เพิ่มท็อปปิ้งไม่ถูกรวมกับจานธรรมดา

## 3.2.10 ระบบกะการทำงานและกระทบยอดเงินสด (Shift & Cash Reconciliation)

> เพิ่มเข้ามาเป็นโมดูลทางการในเวอร์ชันนี้ — เดิมมีรายละเอียดอยู่แล้วในเอกสาร Business Rules หัวข้อ 9 แต่ยังไม่เคยถูกยกเป็นหัวข้อ Scope ระดับ Proposal มาก่อน

- ระบบผูก **กะการทำงาน (Shift) กับรอบวันขายของร้าน (Business Date)** ไม่ผูกกับพนักงานรายคน — 1 วันมี 1 กะเท่านั้น ใช้ Cash Drawer เดียวร่วมกันทั้งร้าน
- พนักงานเปิดกะโดยระบุยอดเงินสดตั้งต้น (Opening Cash) และระบบบันทึกไว้ว่าใครเป็นผู้เปิดกะ (`opened_by`)
- **[แก้ไขรอบ 4]** ระบบบังคับว่า **ต้องมีกะที่เปิดอยู่ก่อน จึงจะเปิดโต๊ะและรับชำระเงินได้** เพื่อให้เงินทุกบาทเข้ากะใดกะหนึ่งเสมอ หากไม่บังคับ กฎ "ปิดกะเท่ากับปิดร้าน" จะอยู่แค่ในเอกสาร และเงินที่รับหลังปิดกะจะไม่เข้ากะใดเลยโดยไม่มีใครรู้
- เมื่อสิ้นกะ พนักงานนับเงินสดจริงและกรอกยอด (Actual Closing Cash) ระบบคำนวณยอดที่ควรมี (Expected Closing Cash) อัตโนมัติ และแสดงผลต่าง (Variance)
- **[แก้ไขรอบ 4]** สูตรยอดที่ควรมีรวมรายการเงินเข้า-ออกลิ้นชักที่ไม่ใช่การขายด้วย (เช่น หยิบเงินไปซื้อน้ำแข็ง แลกธนบัตรย่อย) ตามสูตร `ยอดตั้งต้น + ยอดขายเงินสด + เงินเข้าลิ้นชัก − เงินออกจากลิ้นชัก` หากไม่มีกลไกนี้ ยอดจะไม่ตรงเกือบทุกวันจนไม่มีใครสนใจตรวจสอบผลต่างอีก — การบันทึกเงินเข้า-ออกต้องมีสิทธิ์ `cash:movement` ซึ่งไม่ได้มอบให้พนักงาน เพื่อป้องกันการสร้างรายการปลอมกลบส่วนต่าง
- หากยอดตรงกันพอดี ระบบปิดกะให้อัตโนมัติ โดยไม่ต้องรอการตรวจสอบเพิ่มเติม
- หากยอดไม่ตรงกัน ระบบต้องรอการตรวจสอบและยืนยันจากผู้จัดการ ก่อนปิดกะอย่างเป็นทางการ
- หากผู้จัดการไม่ดำเนินการตรวจสอบภายในระยะเวลาที่ร้านกำหนดได้เอง ระบบจะส่งต่อการตรวจสอบให้เจ้าของร้านแทน
- การเปิดกะของวันถัดไปสามารถทำได้ตามปกติ แม้กะของวันก่อนหน้าจะยังค้างการตรวจสอบอยู่ก็ตาม (ไม่ Block การขาย)
- **[แก้ไขรอบ 4] การเปิดกะที่ปิดไปแล้วใหม่ (Reopen)** เนื่องจากการปิดกะมีความหมายว่าปิดร้านสำหรับวันนั้น หากพนักงานกดปิดผิดระหว่างวันจะขายต่อไม่ได้ ระบบจึงให้ Owner และ Manager เปิดกะใหม่ได้ โดยต้องระบุเหตุผล ระบบนับจำนวนครั้งที่เปิดใหม่ และบันทึกลง Audit Log พร้อมสถานะกับยอดเดิม — **เปิดใหม่ไม่ได้** หากกะนั้นผ่านการรับรองยอดไปแล้ว เพราะถือเป็นหลักฐานทางบัญชีที่ปิดแล้ว และการเปิดใหม่จะไม่ล้างยอดเงินเปิดกะเดิม เพื่อไม่ให้แก้ยอดตั้งต้นให้ตรงกับที่นับได้ภายหลัง
- **ข้อจำกัดที่ยอมรับโดยตั้งใจ:** เนื่องจากใช้ Cash Drawer ร่วมกันทั้งกะ ระบบตรวจสอบผลต่างได้เฉพาะระดับกะ (รายวัน) เท่านั้น ไม่สามารถระบุได้ว่าพนักงานคนใดเป็นสาเหตุของเงินขาด/เกิน — เหมาะสมกับร้านอาหารขนาดเล็กที่มีพนักงานน้อยคนและมีความไว้วางใจกันในระดับสูง

## 3.2.11 ระบบรองรับการทำงานแบบ Offline

- รองรับเฉพาะโมดูลเมนูและการสั่งอาหาร (Menu, Order) เท่านั้น
- ใช้ Service Worker (Workbox) และ IndexedDB (Dexie.js) ในการจัดเก็บข้อมูลชั่วคราว
- ซิงค์ข้อมูลกลับเซิร์ฟเวอร์อัตโนมัติเมื่อการเชื่อมต่ออินเทอร์เน็ตกลับมา
- **[แก้ไขรอบ 4]** กลไกที่ทำให้ซิงค์ซ้ำได้โดยไม่เกิดข้อมูลซ้ำ คือรหัสของใบสั่งอาหารและรายการอาหารเป็น UUID ที่ **อุปกรณ์สร้างเองได้โดยไม่ต้องถามเซิร์ฟเวอร์** ทำให้ขณะออฟไลน์ยังสั่งอาหารได้ และเมื่อซิงค์กลับ ระบบใช้วิธีข้ามแถวที่มีรหัสเดิมอยู่แล้ว การกดซิงค์ซ้ำจึงไม่สร้างบิลซ้ำ — นี่เป็นเหตุผลหลักที่ไม่เปลี่ยนรหัสใบสั่งอาหารไปเป็นเลขรันตามวันที่ ซึ่งต้องถามเซิร์ฟเวอร์ก่อนจึงจะรู้ค่าถัดไป

> **[แก้ไขรอบ 3]** ประเด็น Offline Inventory Conflict ที่เคยเป็น Open Item (อ้างอิง Business Rules ข้อ `INV-04` เดิม) **ถูกปิดจบไปเองแล้ว** หลังเปลี่ยน Inventory เป็น Periodic Physical Count — ไม่มีการตัดสต็อกอัตโนมัติตอนสั่งอาหารอีกต่อไป จึงไม่มี Concurrent Deduction ให้เกิด Conflict ระหว่างออเดอร์หลายรายการที่ Sync พร้อมกันได้เลย

## 3.3 สิ่งที่ระบบไม่รองรับใน MVP นี้ (Out-of-Scope)

| รายการ | เหตุผล |
|---|---|
| Split Bill (แบ่งจ่ายบิล) | **[แก้ไขรอบ 4]** เหตุผลเดิมที่ระบุว่า "ขัดกับหลักการ Immutable Payment" ไม่ถูกต้อง เพราะการแบ่งจ่ายไม่ได้แก้รายการชำระเงินที่บันทึกแล้ว เหตุผลจริงคือเชิงโครงสร้าง: ระบบปัจจุบันอ้างอิงการชำระเงินที่ระดับใบสั่งอาหาร การรองรับแบ่งจ่ายต้องเปลี่ยนไปอ้างอิงที่ระดับรายการอาหาร ซึ่งกระทบตารางและตรรกะจำนวนมาก จึงเลื่อนไปเวอร์ชันถัดไป |
| Refund | เป็นแนวคิดจากระบบ Retail เดิม ไม่สอดคล้องกับบริบทธุรกิจร้านอาหาร — กรณีต้องยกเลิกมูลค่าของรายการที่เสิร์ฟไปแล้ว ระบบใช้กลไก **Comp (Complimentary)** แทน คือปรับราคารายการนั้นเป็น 0 พร้อมบันทึกเหตุผลและผู้อนุมัติ โดยรายการยังคงอยู่ในบิลและ Audit Trail (ไม่ใช่การคืนเงินจริง) |
| ใบกำกับภาษีแบบเต็มรูปตามกฎหมาย | **[แก้ไขรอบ 4]** ระบบรองรับองค์ประกอบพื้นฐานบางส่วนแล้ว คือเลขที่เอกสารต่อเนื่องต่อวันทำการ เลขประจำตัวผู้เสียภาษีของร้าน และการแยกแสดงมูลค่าสินค้ากับภาษี แต่ยังไม่ครบตามข้อกำหนดใบกำกับภาษีเต็มรูป (เช่น ข้อมูลผู้ซื้อ) และ**เอกสารชุดนี้ไม่ได้ยืนยันข้อกฎหมายใด** เจ้าของกิจการต้องตรวจสอบกับกรมสรรพากรหรือผู้ทำบัญชีเอง |
| การปัดเศษยอดสุทธิ | **[เพิ่มรอบ 4]** คอลัมน์รองรับมีอยู่แล้วในฐานข้อมูลแต่ถูกบังคับเป็น 0 ไว้ เพราะยังไม่มีตรรกะการปัดเศษจริง — เลื่อนไปเวอร์ชันถัดไปเพื่อไม่ให้มีตัวเลือกตั้งค่าที่ปรับได้แต่ไม่มีผล |
| การพิมพ์ผ่านเครื่องพิมพ์ความร้อนโดยตรง (Thermal Printer) | ต้องอาศัย Native Wrapper (Capacitor/Tauri) ซึ่งอยู่นอกขอบเขตสถาปัตยกรรม PWA ของโครงงานนี้ |
| การทำงานแบบ Offline สำหรับ Inventory, Payment, Kitchen Display System | ป้องกันความขัดแย้งของข้อมูล (Data Conflict) ที่อาจเกิดจากการยืนยันการชำระเงินซ้ำซ้อนขณะไม่มีการเชื่อมต่อ |
| Export ข้อมูลเป็น CSV | Nice-to-have — จะพิจารณาเพิ่มเติมหากดำเนินการโมดูลหลักเสร็จก่อนกำหนด |
| Supplier Management, Customer/Loyalty, Promotion, Reports เชิงลึก | Tier 2 — วางแผนพัฒนาในเฟสถัดไป |
| Reservation, QR Ordering, Delivery, Gift Card | Tier 3 / Phase 2 — เลื่อนออกไปนอกขอบเขต MVP |
| การรวมโต๊ะแสดงเป็นใบเดียวบนจอครัว | **[เพิ่มรอบ 4]** การชำระเงินรวมหลายโต๊ะทำได้แล้ว สิ่งที่ยังไม่รองรับคือการแสดงรายการของสองโต๊ะเป็นชุดเดียวบนจอครัว |

## หมายเหตุ — สถานะความพร้อมสำหรับเริ่มพัฒนา

เอกสารนี้เป็น **Scope ระดับ Requirement** สำหรับใช้ใน Proposal เท่านั้น
สถานะความพร้อมของเอกสารประกอบที่จำเป็นก่อนเริ่มพัฒนาแต่ละโมดูล มีดังนี้

1. **ERD / Database Schema — เสร็จแล้ว** **[แก้ไขรอบ 4]**
   ความสัมพันธ์ Payment-Order ที่รองรับการรวมบิลได้ข้อสรุปเป็น **1 Payment : N Order** ผ่าน `orders.payment_id` (ดู Business Rules ข้อ PAY-01)
   โครงสร้างฐานข้อมูลฉบับเต็มประกอบด้วย **28 ตาราง และ 3 View** ติดตั้งและทดสอบจริงแล้วบน PostgreSQL 16.13 พร้อม Trigger บังคับกฎทางธุรกิจ 40 ตัว และ Row-Level Security 24 Policy สำหรับการแยกข้อมูลระหว่างร้าน
   *(ตัวเลข 23 ตารางในเอกสารรอบ 3 เป็นการนับก่อนออกแบบรอบสุดท้าย ซึ่งยังไม่มีตารางนิยามค่าตั้งค่า ตารางตัวนับเลขที่เอกสาร ตารางเงินเข้า-ออกลิ้นชัก และตารางย่อยของการชำระเงิน)*
   เอกสารอ้างอิง: `claude/data-dictionary-v2.md` (คำอธิบายทุกตาราง) และ `claude/database-design-revision.md` (บันทึกเหตุผลการออกแบบและผลทดสอบ)
2. **API Contract — ยังไม่เสร็จ** endpoint และรูปแบบ request/response ของแต่ละโมดูล
3. **UI/UX Flow — ยังไม่เสร็จ** รายละเอียดหน้าจอและการโต้ตอบของผู้ใช้

**คำแนะนำ [ปรับรอบ 4]:** เนื่องจากโครงสร้างฐานข้อมูลนิ่งแล้ว ข้อจำกัดเดิมที่ให้ชะลอการเชื่อม state/API ของโมดูล Order/Payment/Bill Merge จึงไม่จำเป็นอีก งานที่ควรทำก่อนเริ่มพัฒนาโมดูลเหล่านี้คือการปรับฝั่ง NestJS ให้สอดคล้องกับฐานข้อมูลใหม่ ได้แก่ การเปลี่ยนบัญชีเชื่อมต่อฐานข้อมูลเป็นบัญชีที่ถูกบังคับด้วย Row-Level Security การกำหนด Session Context ทุก Request และการปิดกลไก Auto-sync Schema ของ ORM — รายการทั้งหมดอยู่ในหัวข้อ 9 ของ `claude/database-design-revision.md`
