## 1. บทนำ

เอกสารฉบับนี้บันทึกการทบทวนการออกแบบฐานข้อมูล PWA-POS ที่ดำเนินการก่อนนำระบบขึ้นใช้งานจริง (Production) การทบทวนครอบคลุมสามมิติ ได้แก่ ความถูกต้องของข้อมูล (Data Integrity) ความปลอดภัยในสถาปัตยกรรม Multi-tenant และความสอดคล้องกับกระบวนการทำงานจริงของร้านอาหารขนาดเล็ก

ผลการทบทวนพบข้อบกพร่องที่ต้องแก้ไข 6 ประการ ช่องโหว่เชิงออกแบบ 11 ประการ และประเด็นที่ต้องตัดสินใจเชิงขอบเขต 11 ประการ ซึ่งได้ดำเนินการแก้ไขและบันทึกเหตุผลไว้ในเอกสารนี้ทั้งหมด

## 2. ข้อบกพร่องที่พบจากการทดสอบและการแก้ไข

### 2.1 การเขียนข้อมูลข้ามร้านผ่าน Foreign Key

**ปัญหาที่พบ** การทดสอบบนฐานข้อมูลจริงพบว่าสามารถสร้างใบสั่งอาหาร (Order) ของร้าน A โดยผูกกับโต๊ะของร้าน B ได้สำเร็จ

**สาเหตุ** Row-Level Security ควบคุมการ **อ่าน** ข้อมูลข้ามร้านได้ แต่ไม่ได้ควบคุมการ **เขียน** Foreign Key ที่ชี้ไปยังแถวของร้านอื่น เนื่องจาก Foreign Key Constraint ถูกตรวจสอบในระดับ Referential Integrity ซึ่งไม่ผ่าน RLS Policy

**ผลกระทบ** ข้อมูลของร้านหนึ่งสามารถอ้างอิงข้อมูลของอีกร้านหนึ่งได้ ซึ่งละเมิดหลัก Tenant Isolation อันเป็นหัวใจของสถาปัตยกรรม Multi-tenant

**การแก้ไข** เปลี่ยน Foreign Key ทุกจุดที่ข้ามตารางเป็น **Composite Foreign Key** ที่รวม `tenant_id` เข้าไปด้วย

```sql
-- เดิม
table_id UUID NOT NULL REFERENCES dining_tables(table_id)

-- ใหม่
CONSTRAINT uq_dining_tables_tenant_table UNIQUE (tenant_id, table_id)   -- ที่ตารางแม่
FOREIGN KEY (tenant_id, table_id) REFERENCES dining_tables (tenant_id, table_id)
```

แนวทางนี้เป็นแนวทางเดียวกับที่ Citus (ส่วนขยาย PostgreSQL สำหรับ Multi-tenant) แนะนำอย่างเป็นทางการ ผลการทดสอบหลังแก้ไขพบว่าการเขียนข้ามร้านถูกปฏิเสธที่ระดับฐานข้อมูล

### 2.2 รายการชำระเงินสามารถถูกแก้ไขและลบได้

**ปัญหาที่พบ** เอกสารระบุหลัก Immutable Payment ไว้ แต่ฐานข้อมูลไม่ได้บังคับใช้ และ `orders.payment_id` ใช้ `ON DELETE SET NULL` ซึ่งหมายความว่าหากรายการชำระเงินถูกลบ ใบสั่งอาหารจะกลับไปอยู่ในสถานะยังไม่ชำระโดยไม่มีร่องรอย

**การแก้ไข** บังคับใช้ 3 ชั้น

1. Trigger `immutable` ปฏิเสธทุก `UPDATE` และ `DELETE` บน `payments`, `inventory_transactions`, `receipt_print_logs`, `cash_movements`
2. `REVOKE UPDATE, DELETE` จาก Database Role ที่แอปพลิเคชันใช้
3. เปลี่ยน Foreign Key เป็น `NO ACTION` แทน `SET NULL`

ตาราง `audit_logs` ใช้ Trigger แยกที่อนุญาตให้ลบได้เฉพาะแถวที่มีอายุเกิน 1 ปี ผ่านฟังก์ชัน `purge_old_audit_logs()`

### 2.3 ความคิดเห็นในโค้ดไม่ตรงกับพฤติกรรมจริง

**ปัญหาที่พบ** `menu_items.category_id` ระบุความคิดเห็นว่าเป็น `RESTRICT` แต่โค้ดจริงใช้ `CASCADE` ทำให้การลบหมวดหมู่หนึ่งจะลบเมนูทั้งหมดในหมวดนั้นไปโดยเงียบ ทั้งที่ระบบใช้ Soft Delete ผ่านคอลัมน์ `is_active` อยู่แล้ว

**การแก้ไข** เปลี่ยนเป็น `NO ACTION` และลบความคิดเห็นที่ขัดแย้งออก

### 2.4 การออกเลขที่ใบเสร็จแบบ MAX()+1

**ปัญหาที่พบ** การหาเลขที่ใบเสร็จถัดไปด้วย `MAX(receipt_number) + 1` จะเกิด Race Condition เมื่อมีการชำระเงินพร้อมกันจากสองเครื่อง ทำให้เกิดการละเมิด Unique Constraint และรายการชำระเงินล้มเหลว

**การแก้ไข** สร้างตาราง Counter แยก (`receipt_sequences`, `order_sequences`) และใช้ `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` ซึ่งเป็นการดำเนินการแบบ Atomic ภายในคำสั่งเดียว

```sql
INSERT INTO receipt_sequences(tenant_id, business_date, last_no) VALUES (p_tenant, p_bdate, 1)
ON CONFLICT (tenant_id, business_date) DO UPDATE SET last_no = receipt_sequences.last_no + 1
RETURNING last_no INTO n;
```

ผลการทดสอบด้วยการชำระเงินพร้อมกัน 20 รายการจากกระบวนการแยกกัน 20 กระบวนการ ได้เลขที่ใบเสร็จต่อเนื่องครบถ้วนโดยไม่ซ้ำและไม่ข้ามเลข (ดูหัวข้อ 7.1)

### 2.5 ใบสั่งอาหารบางกรณีปิดไม่ได้

**ปัญหาที่พบ** ตาราง `orders` ไม่มีคอลัมน์ระบุว่าปิดแล้วหรือยัง สถานะอนุมานจาก `payment_id IS NOT NULL` เพียงอย่างเดียว ทำให้กรณีที่ลูกค้าเดินออกไปโดยไม่สั่ง ลูกค้าเบี้ยวบิล หรือรายการถูกยกเลิกทั้งหมด ใบสั่งอาหารจะค้างอยู่ตลอดไปและโต๊ะจะไม่กลับมาว่าง

นอกจากนี้ `payment_attempts.amount` มี `CHECK (amount > 0)` ทำให้บิลที่ถูก Comp ครบทุกรายการ (ยอด 0 บาท) ชำระเงินไม่ได้

**การแก้ไข** เพิ่ม `closed_at`, `closed_by`, `close_reason` โดย `close_reason` รับค่า `paid`, `voided_all`, `empty`, `walkout` และเปลี่ยน `CHECK` ของยอดเป็น `>= 0`

### 2.6 ไม่มีข้อมูลตั้งต้นและไม่มี Row-Level Security

**ปัญหาที่พบ** DDL ชุดเดิมไม่มีข้อมูล `roles`, `permissions`, `role_permissions` ทั้งที่ `users.role_id` เป็น `NOT NULL` ทำให้สมัครบัญชีเจ้าของร้านไม่ได้เลย และไฟล์ DDL ทุกไฟล์ระบุว่า RLS "แยกไฟล์" แต่ไฟล์นั้นไม่มีอยู่จริง

**การแก้ไข** รวมข้อมูลตั้งต้นและ RLS Policy เข้าไปในไฟล์ติดตั้งเดียวกัน

## 3. การเปลี่ยนแปลงเชิงขอบเขต (Scope Decisions)

### 3.1 ยกเลิกการตัดสต็อกอัตโนมัติ

**การตัดสินใจ** ไม่สร้างตารางสูตรอาหาร (Recipe / Bill of Materials) ที่ผูกวัตถุดิบเข้ากับเมนู และเปลี่ยนเป็นให้พนักงานกรอกยอดวัตถุดิบคงเหลือเองเมื่อสิ้นวัน

**เหตุผล** ร้านอาหารตามสั่งไม่ได้ทำอาหารตามสูตรที่ชั่งตวงแน่นอน การบังคับให้เจ้าของร้านกรอกปริมาณวัตถุดิบต่อจานทุกเมนูเป็นภาระที่ทำให้ระบบไม่ถูกใช้งาน และยอดที่ได้ก็ไม่ตรงกับความจริงอยู่ดี

**สิ่งที่ตัดตามไปด้วย** เนื่องจากไม่มีการตัดสต็อกอัตโนมัติ คอลัมน์และค่าต่อไปนี้จึงไม่มีวันถูกใช้งานและถูกตัดออก

- `inventory_transactions.type = 'deduction'`
- `inventory_transactions.order_item_id` และ Foreign Key ที่ชี้ไป `order_items`
- Index `idx_inventory_transactions_order_item`

**ประเภทรายการที่เหลือ** `restock` (ซื้อของมาเติม) · `adjustment` (กรอกยอดคงเหลือ) · `waste` (ของเสีย) โดยรวม `purchase` เดิมเข้ากับ `restock` เพราะสื่อความหมายเดียวกัน

**กลไกทดแทน** ฟังก์ชัน `record_stock_count()` รับยอดที่นับได้ คำนวณส่วนต่างเทียบกับ Ledger แล้วบันทึกเป็นรายการ `adjustment` พร้อมเก็บยอดที่นับได้จริงไว้ในคอลัมน์ `counted_quantity` โดยล็อกแถววัตถุดิบไว้ระหว่างคำนวณเพื่อป้องกัน Race Condition กับการรับของที่อาจเกิดขึ้นพร้อมกัน

### 3.2 ไม่มีคอลัมน์จำนวนในรายการสั่งอาหาร

**การตัดสินใจ** คงการออกแบบที่ 1 จาน = 1 แถว ไม่เพิ่มคอลัมน์ `quantity`

**เหตุผล** แต่ละจานมีสถานะของตัวเองบนจอครัว ทำให้เสิร์ฟทีละจานได้ ยกเลิกเฉพาะจานที่ลูกค้าเปลี่ยนใจได้ และ Comp เฉพาะจานที่ทำพลาดได้ โดยไม่ต้องแตกแถวภายหลัง เป็นแนวทางเดียวกับที่ Toast และ Square ใช้

**ผลที่ตามมา** ใบเสร็จต้องรวมรายการที่เหมือนกันเองผ่าน View `v_receipt_lines` โดยจัดกลุ่มตามราคาและชุด Modifier ไม่ใช่ตามเมนูอย่างเดียว เพื่อไม่ให้จานที่เพิ่มไข่ดาวถูกรวมกับจานธรรมดา

ตัวอย่างผลลัพธ์เมื่อสั่งกระเพราหมู 3 จาน จานที่ 3 เพิ่มไข่ดาว

| ราคาต่อหน่วย | จำนวน | รวม | ท็อปปิ้ง |
|---|---|---|---|
| 60.00 | 2 | 120.00 | |
| 70.00 | 1 | 70.00 | ไข่ดาว |

### 3.3 หนึ่งกะต่อหนึ่งวันทำการ และการเปิดกะใหม่

**การตัดสินใจ** คง Unique Constraint `(tenant_id, business_date)` ไว้ การกดปิดกะมีความหมายว่าปิดร้านสำหรับวันนั้น

**ปัญหาที่ตามมา** หากพนักงานกดปิดกะผิดระหว่างวัน จะขายต่อไม่ได้และเปิดกะใหม่ไม่ได้

**การแก้ไข** เพิ่มฟังก์ชัน `reopen_shift(shift_id, user_id, reason)` ที่

- ตรวจสอบสิทธิ์ `shift:reopen` (Manager และ Owner เท่านั้น)
- บังคับให้ระบุเหตุผล หากเว้นว่างจะถูกปฏิเสธ
- เปิดได้เฉพาะกะที่สถานะเป็น `closed_auto` หรือ `pending_verification`
- **ไม่อนุญาต** ให้เปิดกะที่สถานะ `verified` หรือ `escalated` เนื่องจากผ่านการรับรองโดยผู้มีอำนาจแล้ว ถือเป็นหลักฐานทางบัญชีที่ปิดแล้ว การเปิดใหม่จะขัดกับหลัก Immutable เช่นเดียวกับรายการชำระเงิน
- ล้างยอดปิดกะเดิม (`actual_closing_cash`, `expected_closing_cash`, `closed_at`, `closed_by`) แต่ **คงยอดเงินเปิดกะเดิมไว้** เพื่อไม่ให้แก้ยอดเปิดให้ตรงกับที่นับได้ภายหลัง
- เพิ่มตัวนับ `reopen_count` และเขียน Audit Log ประเภท `shift_reopened` พร้อมบันทึกสถานะเดิมและยอดเดิมไว้ใน Metadata

**เหตุผลที่ไม่สร้างตาราง Log แยก** ตาราง `audit_logs` มีโครงสร้างที่ครบถ้วนอยู่แล้ว ทั้ง `tenant_id`, `user_id`, `ip_address`, `device_info` และ `metadata` แบบ JSONB การสร้างตารางแยกจะทำให้ได้บันทึกที่ขาดข้อมูลบริบทเมื่อเทียบกับบันทึกอื่นในระบบ และทำให้หน้า Audit Log ต้องอ่านจากสองแหล่ง

### 3.4 เงินทุกบาทต้องเข้ากะ

**การตัดสินใจ** ห้ามเปิดใบสั่งอาหารและห้ามบันทึกการชำระเงิน หากไม่มีกะที่สถานะ `open` ของวันทำการนั้น

**เหตุผล** หากไม่บังคับ กฎ "ปิดกะเท่ากับปิดร้าน" จะอยู่แค่ในเอกสาร เมื่อพนักงานปิดกะแล้วมีลูกค้าเข้ามาอีก เงินที่รับจะไม่เข้ากะใดเลยและยอดกระทบไม่ตรงโดยไม่มีใครรู้

**กลไกรองรับ** `shifts.business_date` ไม่ให้กรอกเอง แต่คำนวณจาก `compute_business_date()` เช่นเดียวกับ `payments.business_date` ทำให้ทั้งสองค่ามาจากแหล่งเดียวกันเสมอ ไม่มีโอกาสเหลื่อมกัน

### 3.5 การยกเลิกรายการขณะครัวกำลังทำ

**การตัดสินใจ** อนุญาตให้ Void ได้ทั้งสถานะ `queued` และ `preparing` โดยการ Void ขณะ `preparing` ต้องมีสิทธิ์ `void:approve` และระบุเหตุผล ส่วนรายการที่เสิร์ฟแล้วใช้กลไก Comp แทน

**เหตุผล** การออกแบบเดิมอนุญาต Void เฉพาะ `queued` และ Comp เฉพาะ `served` ทำให้กรณีที่ลูกค้าขอยกเลิกขณะครัวกำลังทำ พนักงานต้องรอจนทำเสร็จ เสิร์ฟออกไป แล้วค่อย Comp ซึ่งไม่ตรงกับหน้างานจริง

### 3.6 ภาษีมูลค่าเพิ่ม

**การตัดสินใจ** รองรับ 3 โหมดผ่าน Configuration โดยค่าเริ่มต้นคือ `none`

| โหมด | ความหมาย | เมนู 60 บาท ลูกค้าจ่าย |
|---|---|---|
| `none` | ไม่จดทะเบียนภาษีมูลค่าเพิ่ม (ค่าเริ่มต้น) | 60.00 |
| `inclusive` | ราคาเมนูรวมภาษีแล้ว | 60.00 |
| `exclusive` | บวกภาษีเพิ่มจากราคา | 64.20 |

**เหตุผลที่ `none` เป็นค่าเริ่มต้น** ร้านอาหารขนาดเล็กจำนวนมากไม่ได้จดทะเบียนภาษีมูลค่าเพิ่ม หากตั้งค่าเริ่มต้นเป็นโหมดที่มีภาษี ร้านเหล่านี้จะออกเอกสารที่มีรายการภาษีโดยไม่ตั้งใจ ซึ่งเป็นความผิดพลาดที่ร้ายแรงกว่าการไม่ออก

**กลไกป้องกัน** Trigger ปฏิเสธการเปลี่ยน `vat_mode` ออกจาก `none` หากร้านยังไม่ได้กรอก `tenants.tax_id` เนื่องจากเอกสารกำกับภาษีต้องแสดงเลขประจำตัวผู้เสียภาษี

**วิธีคำนวณโหมด `inclusive`** แกะภาษีออกจากยอดรวม แล้วหาราคาสินค้าจากส่วนที่เหลือ

```
vat_amount = ROUND(total - (total / (1 + rate/100)), 2)
subtotal   = total - vat_amount - service_charge - rounding
```

การคำนวณในลำดับนี้ทำให้ตัวเลขบนเอกสารบวกกันได้เท่ากับยอดรวมเสมอ หากคำนวณภาษีแยกแล้วนำมาบวกกันจะเกิดผลต่าง 1 สตางค์ในบางยอด

ผลการทดสอบกับยอด 70 บาท อัตรา 7% ได้ มูลค่าสินค้า 65.42 ภาษี 4.58 รวม 70.00

**การเก็บ Snapshot** ทุกรายการชำระเงินบันทึก `vat_mode`, `vat_rate_snapshot` และ `service_charge_rate_snapshot` ไว้ในแถวของตนเอง ทำให้พิมพ์เอกสารย้อนหลังได้ถูกต้องแม้อัตราภาษีจะเปลี่ยนไปแล้ว

**คำเตือน** การเปลี่ยน `vat_mode` จาก `inclusive` เป็น `exclusive` จะทำให้ราคาเมนูเดิมทั้งร้านมีความหมายเปลี่ยนไปทันที ระบบควรแจ้งเตือนให้ตรวจสอบราคาเมนูใหม่ทั้งหมด

> **หมายเหตุด้านกฎหมาย** เกณฑ์รายได้ที่ต้องจดทะเบียนภาษีมูลค่าเพิ่ม และข้อกำหนดเรื่องการแสดงราคารวมภาษี เป็นเรื่องที่เจ้าของกิจการต้องตรวจสอบกับกรมสรรพากรหรือผู้ทำบัญชีเอง เอกสารฉบับนี้ไม่ได้ยืนยันข้อกฎหมายใด และระบบไม่ได้ฝังเกณฑ์รายได้ไว้

### 3.7 เลขที่ใบสั่งอาหารสำหรับการสื่อสารหน้างาน

**ปัญหา** `order_id` เป็น UUID ซึ่งพนักงานเรียกกันปากเปล่าไม่ได้

**ทางเลือกที่พิจารณาแล้วปฏิเสธ** เปลี่ยน Primary Key เป็นเลขรันรูปแบบ `YYYYMMDDTT` ปฏิเสธด้วยเหตุผล 4 ประการ

1. **ชนกันระหว่างร้าน** เลขรันตามวันที่เป็นค่าเดียวกันในทุกร้าน หากใช้เป็น Primary Key ร้านที่สองจะสร้างใบสั่งอาหารแรกของวันไม่ได้ หากแก้โดยรวม `tenant_id` เข้าไปจะได้ค่าที่ยาวกว่า UUID และยังพูดปากเปล่าไม่ได้อยู่ดี
2. **ขัดกับการทำงานแบบออฟไลน์** เลขรันต้องสอบถามฐานข้อมูลก่อนจึงจะรู้ค่าถัดไป เมื่อเครือข่ายขาด อุปกรณ์จะสร้างใบสั่งอาหารไม่ได้เลย ซึ่งขัดกับเหตุผลหลักของการเลือกสถาปัตยกรรม Progressive Web Application ในทางกลับกัน UUID อุปกรณ์สร้างเองได้ แล้วซิงค์ภายหลังด้วย `INSERT ... ON CONFLICT DO NOTHING`
3. **คาดเดาได้** เลขรันทำให้ไล่ดูใบสั่งอาหารของคนอื่นภายในร้านเดียวกันได้ผ่าน API
4. **กระทบ Foreign Key ทุกตาราง** ที่อ้างถึง `order_id`

**การตัดสินใจ** คง `order_id` เป็น UUID และเพิ่มคอลัมน์ `order_number` แยกต่างหาก เป็นเลขจำนวนเต็มที่รันใหม่ทุกวันทำการ ใช้กลไก Counter เดียวกับเลขที่ใบเสร็จ

แนวทางนี้เป็นแนวทางเดียวกับที่ Shopify ใช้ (`id` ภายใน กับ `name` ที่ลูกค้าเห็น) และ Stripe ใช้ (`in_1A2b3C...` กับ `invoice_number`)

### 3.8 การบังคับกฎเมนูในระดับฐานข้อมูล

| กฎ | บังคับที่ใด | เหตุผล |
|---|---|---|
| `menu_items.is_available = false` สั่งไม่ได้ | Trigger ในฐานข้อมูล | หากหลุดไปจะเกิดรายการที่ครัวทำไม่ได้ และกระทบเงิน |
| `modifier_groups.is_required` ต้องเลือก | ฝั่ง Frontend เท่านั้น | Modifier ถูกบันทึกหลังรายการสั่งอาหาร ฐานข้อมูลจึงยังไม่ทราบว่าผู้ใช้เลือกครบหรือยัง ณ เวลาที่บันทึก |

### 3.9 การตรวจจับส่วนต่างสต็อกผิดปกติ

เมื่อพนักงานกรอกยอดวัตถุดิบคงเหลือ ระบบจะเขียน Audit Log ประเภท `inventory_adjusted` อัตโนมัติ เมื่อเข้าเงื่อนไขทั้งสองข้อพร้อมกัน

1. ส่วนต่างเกิน `inventory_variance_alert_percent` (ค่าเริ่มต้น 20%) ของยอดที่ระบบคิด
2. ส่วนต่างสัมบูรณ์มากกว่า 1 หน่วย

**เหตุผลที่ใช้สัดส่วนร้อยละแทนจำนวนคงที่** วัตถุดิบแต่ละชนิดมีหน่วยและขนาดต่างกันมาก ผงปรุงรส 50 กรัมคือปริมาณมาก ขณะที่เนื้อหมู 50 กรัมคือเศษ การใช้เกณฑ์เป็นจำนวนคงที่จึงใช้ไม่ได้

**เหตุผลที่ต้องเข้าเงื่อนไขทั้งสองข้อ** หากใช้สัดส่วนอย่างเดียว วัตถุดิบที่เหลือน้อยมาก เช่น เหลือ 10 กรัมแล้วนับได้ 0 จะคิดเป็นส่วนต่าง 100% และยิงการแจ้งเตือนทุกวันทั้งที่เป็นเรื่องปกติ

**เหตุผลที่กำหนดเป็น Configuration ไม่ใช่ค่าคงที่ในโค้ด** ร้านที่ขายของสดซึ่งมีการสูญเสียตามธรรมชาติสูง ส่วนต่าง 20% อาจเป็นเรื่องปกติ เจ้าของร้านจึงควรปรับเกณฑ์เองได้โดยไม่ต้องรอการปรับปรุงระบบ

### 3.10 การลบ Configuration ที่ไม่มีผู้ใช้งาน (`rounding_mode`)

**ปัญหาที่พบ** การตรวจสอบรอบสุดท้ายพบว่า Configuration ชื่อ `rounding_mode` ถูกนิยามไว้ใน `config_definitions` และถูกสร้างให้ร้านใหม่ทุกร้านอัตโนมัติ แต่ไม่มี Trigger, View, ฟังก์ชัน หรือโค้ดส่วนใดในระบบอ่านค่านี้ไปใช้เลยแม้แต่จุดเดียว

**ผลกระทบ** เจ้าของร้านเห็นตัวเลือกการปัดเศษในหน้าตั้งค่า ปรับค่าได้ ระบบบันทึกค่าให้ แต่พฤติกรรมการคำนวณไม่เปลี่ยน นี่คือ Configuration ที่หลอกผู้ใช้ และเป็นหนี้ทางเทคนิคที่ยากต่อการตรวจจับภายหลัง เพราะโครงสร้างดูสมบูรณ์ทุกอย่างยกเว้นผู้บริโภคค่า

**การแก้ไข**

1. ลบแถว `rounding_mode` ออกจากข้อมูลตั้งต้นของ `config_definitions` จำนวน Configuration จึงเหลือ 9 รายการ
2. เพิ่ม `CHECK (rounding_adjustment = 0)` บนตาราง `payments` เพื่อบังคับที่ระดับฐานข้อมูลว่าคอลัมน์นี้จะไม่มีค่าอื่นเข้ามาได้ จนกว่าจะมีการพัฒนากลไกการปัดเศษจริง
3. คงคอลัมน์ `rounding_adjustment` ไว้ในสูตรคำนวณ `total = subtotal + vat + service + rounding` เพื่อให้สูตรยังถูกต้องเมื่อเปิดใช้งานในอนาคต

**วิธีเปิดใช้งานในอนาคต** ต้องแก้ 3 จุดพร้อมกัน คือเพิ่มแถว Configuration กลับเข้า `config_definitions` เขียนตรรกะการปัดเศษใน `trg_payments_before()` และผ่อนปรน `CHECK` ข้อ 2 ออก

**เหตุผลที่ `kds_enabled` ไม่ถือเป็นปัญหาเดียวกัน** `kds_enabled` ก็ไม่มี Trigger ใดอ่านเช่นกัน แต่เป็น Configuration ที่ฝั่ง Frontend ใช้ตัดสินใจว่าจะแสดงหน้าจอครัวหรือไม่ ซึ่งเป็นผู้บริโภคค่าที่ถูกต้องตามการออกแบบ ส่วน `rounding_mode` เป็นตรรกะการคำนวณเงินซึ่งต้องอยู่ในฐานข้อมูลเท่านั้น จะยกให้ Frontend คำนวณไม่ได้

**หลักการที่ได้** ทุก Configuration ต้องระบุได้ว่าใครเป็นผู้อ่านค่าไปใช้ ไม่ว่าจะเป็น Trigger ในฐานข้อมูลหรือโค้ดฝั่งใดฝั่งหนึ่ง หากระบุไม่ได้ให้ลบออก (บันทึกเป็นกฎ `CFG-09` ใน `business-rules-pos-updated.md`)

### 4.1 เหตุผลของตาราง `cash_movements`

หากไม่มีตารางนี้ ยอดเงินสดที่ระบบคาดหวังจะคำนวณจากยอดขายเงินสดบวกเงินเปิดกะเท่านั้น เมื่อพนักงานหยิบเงินในลิ้นชักไปซื้อน้ำแข็งหรือแลกธนบัตรย่อย ยอดที่นับได้จะไม่ตรงทุกวัน ทำให้กลไกการกระทบยอดเงินสดสูญเสียความหมาย เพราะมีส่วนต่างเป็นเรื่องปกติจนไม่มีใครสนใจตรวจสอบ

สูตรคำนวณที่ใช้จริง

```
expected_closing_cash = opening_cash + ยอดขายเงินสด + เงินเข้าลิ้นชัก − เงินออกจากลิ้นชัก
```

ตารางนี้เป็นแบบ Append-only และต้องมีสิทธิ์ `cash:movement` ซึ่งไม่ได้มอบให้พนักงาน เพื่อป้องกันการสร้างรายการเงินออกปลอมเพื่อกลบส่วนต่าง

## 6. ความปลอดภัย

### 6.1 Row-Level Security

RLS Policy ถูกสร้างบนทุกตารางที่มีคอลัมน์ `tenant_id` รวม 24 Policy โดยใช้เงื่อนไขเดียวกันทั้ง `USING` และ `WITH CHECK`

ระบบใช้ `ENABLE ROW LEVEL SECURITY` ไม่ใช่ `FORCE` โดยตั้งใจ เพื่อให้เจ้าของ Schema (ที่ใช้รัน Migration และฟังก์ชันประเภท `SECURITY DEFINER`) ข้าม Policy ได้ ส่วนแอปพลิเคชันซึ่งเชื่อมต่อด้วย Role `pos_app` ที่ไม่ใช่เจ้าของและไม่มีสิทธิ์ `BYPASSRLS` จะถูกบังคับใช้ Policy เสมอ

**ข้อควรระวังที่สำคัญที่สุด** หากแอปพลิเคชันเชื่อมต่อด้วย `postgres` RLS จะไม่ทำงานเลยแม้ Policy จะถูกสร้างไว้ครบถ้วน ซึ่งอันตรายกว่าการไม่มี RLS เพราะทำให้เข้าใจผิดว่ามีการป้องกันอยู่

### 6.2 ฟังก์ชันที่ข้าม RLS โดยตั้งใจ

ขั้นตอนการเข้าสู่ระบบยังไม่ทราบว่าผู้ใช้สังกัดร้านใด จึงยังกำหนด Session Context ไม่ได้ ระบบจึงมีฟังก์ชัน `SECURITY DEFINER` สองตัวที่จำกัดขอบเขตการคืนค่าไว้อย่างแคบ

- `resolve_tenant(slug)` คืนเฉพาะรหัสร้านและสถานะใช้งาน
- `resolve_user_by_email(email)` คืนเฉพาะรหัสผู้ใช้และรหัสร้าน

ทั้งสองฟังก์ชันไม่คืนรหัสผ่านหรือข้อมูลอื่น และกำหนด `SET search_path = public, pg_temp` เพื่อป้องกันการโจมตีผ่านการสร้าง Object ชื่อซ้ำใน Schema อื่น

### 6.3 สิทธิ์ของ Database Role

| กลุ่มตาราง | สิทธิ์ของ `pos_app` |
|---|---|
| `roles`, `permissions`, `role_permissions`, `config_definitions` | อ่านอย่างเดียว |
| `payments`, `inventory_transactions`, `receipt_print_logs`, `audit_logs`, `cash_movements` | เพิ่มและอ่านเท่านั้น |

| ตารางอื่น | อ่าน เพิ่ม แก้ไข ลบ |

### 6.4 การป้องกันการเดารหัสผ่านและรหัส PIN

รหัส PIN มีความยาว 4 ถึง 6 หลัก ซึ่งหากฐานข้อมูลรั่วไหลจะถูกถอดรหัสได้ในเวลาไม่นานแม้จะเก็บเป็น Hash ระบบจึงเพิ่มคอลัมน์นับจำนวนครั้งที่ลองผิดและเวลาที่ล็อกบัญชี ทั้งสำหรับรหัสผ่านและรหัส PIN เพื่อให้แอปพลิเคชันบังคับใช้การล็อกชั่วคราว พร้อมเขียน Audit Log เมื่อเกิดการล็อก

## 7. ผลการทดสอบ

ชุดทดสอบ `tests/behavior_test.sql` ครอบคลุม 25 สถานการณ์ และ `tests/rls_test.sql` ครอบคลุม 10 สถานการณ์ ดำเนินการบน PostgreSQL 16.13 ผลการทดสอบผ่านทั้งหมด โดยมีกรณีที่ออกแบบให้ถูกปฏิเสธ 18 กรณีในชุดแรกและ 11 กรณีในชุดที่สอง ซึ่งถูกปฏิเสธจริงตามที่คาดหวัง

ตัวอย่างข้อความแสดงข้อผิดพลาดที่ระบบตอบกลับ

| สถานการณ์ | ข้อความ |
|---|---|
| เปิดบิลโดยยังไม่เปิดกะ | `no open shift for business_date 2026-10-01 (เปิดกะก่อน)` |
| สั่งเมนูที่หมดวันนี้ | `menu item "ต้มยำกุ้ง" is not available today` |
| พนักงานยกเลิกรายการขณะครัวกำลังทำ | `voiding a preparing item requires void:approve` |
| พนักงานยกเว้นค่าอาหาร | `comp requires discount:approve` |
| แก้ไขรายการชำระเงิน | `payments is immutable/append-only (UPDATE blocked)` |
| เปิดใช้ภาษีโดยไม่มีเลขผู้เสียภาษี | `ต้องกรอกเลขประจำตัวผู้เสียภาษี (tenants.tax_id) ก่อนเปิดใช้ VAT` |
| พนักงานเปิดกะที่ปิดแล้วใหม่ | `user lacks permission shift:reopen` |
| เปิดกะที่รับรองแล้วใหม่ | `cannot reopen a verified shift` |
| เขียนข้อมูลโดยไม่มี Session Context | `new row violates row-level security policy for table "tenants"` |

### 7.1 ผลการวัดประสิทธิภาพและการทำงานพร้อมกัน

**ชุดข้อมูลที่ใช้ทดสอบ** สร้างข้อมูลสมมติที่สมจริงย้อนหลัง 90 วันทำการ ประกอบด้วยใบเสร็จ 7,200 รายการ รายการอาหาร 28,800 รายการ ขนาดฐานข้อมูลรวม 29 เมกะไบต์

| คำสั่งค้นข้อมูล | เวลาที่ใช้ |
|---|---|
| ดึงคิวอาหารขึ้นจอครัว | 0.27 มิลลิวินาที |
| เปิดโต๊ะและดึงรายการของใบสั่งอาหาร | 5.7 มิลลิวินาที |
| บันทึกการชำระเงินพร้อมออกเลขที่ใบเสร็จ | 5.8 มิลลิวินาที |
| รายงานเมนูขายดีย้อนหลัง 90 วัน | 9.1 มิลลิวินาที |

**ต้นทุนของ Trigger** การเปรียบเทียบการสร้างใบสั่งอาหารครบวงจรจำนวน 200 รอบ ระหว่างกรณีเปิด Trigger ทั้งหมดกับกรณีปิด Trigger ได้ 398.6 มิลลิวินาที เทียบกับ 140.9 มิลลิวินาที คิดเป็นต้นทุนเพิ่ม **1.29 มิลลิวินาทีต่อหนึ่งรอบใบสั่งอาหาร** ซึ่งเป็นราคาที่ยอมรับได้เมื่อเทียบกับการย้ายกฎเหล่านี้ไปบังคับใช้ฝั่งแอปพลิเคชันแล้วเสี่ยงหลุด

> **ข้อควรระวังจากการทดสอบนี้** การวัดครั้งแรกรายงานผลเพียง 2.121 มิลลิวินาที ซึ่งต่ำผิดปกติ การตรวจสอบจำนวนแถวที่ถูกเขียนจริงพบว่าเป็น 0 แถว เนื่องจากการปิด Trigger ทำให้ `order_number` เป็นค่าว่างและ Constraint ปฏิเสธทุกแถว ผลลัพธ์ที่เร็วผิดปกติจึงมาจากการที่ไม่มีงานเกิดขึ้นเลย ไม่ใช่จากประสิทธิภาพ กรณีนี้เป็นตัวอย่างว่าการวัดประสิทธิภาพต้องตรวจจำนวนแถวที่เปลี่ยนแปลงประกอบทุกครั้ง

**การทดสอบการทำงานพร้อมกัน** ดำเนินการด้วยกระบวนการแยกกันจริงในระดับระบบปฏิบัติการ ไม่ใช่การจำลองในคำสั่งเดียว

| สถานการณ์ | ผลลัพธ์ |
|---|---|
| สองเครื่องเปิดใบสั่งอาหารบนโต๊ะเดียวกันพร้อมกัน | เครื่องที่สองถูกปฏิเสธด้วย Partial Unique Index `uq_orders_one_active_per_table` |
| สองรายการชำระเงินจากการพยายามชำระครั้งเดียวกัน | รายการที่สองถูกปฏิเสธด้วย Partial Unique Index `uq_pao_one_open_per_order` |
| ชำระเงินพร้อมกัน 20 รายการ | ได้เลขที่ใบเสร็จ `011026-0003` ถึง `011026-0022` ต่อเนื่องครบถ้วน ไม่ซ้ำและไม่ข้ามเลข |

### 7.2 ข้อจำกัดของการทดสอบ

1. ข้อมูลทดสอบเป็นข้อมูลสมมติที่สร้างขึ้น ไม่ใช่ข้อมูลจากร้านที่เปิดใช้งานจริง รูปแบบการกระจายตัวของยอดขายจริงอาจต่างออกไป
2. การทดสอบดำเนินการบนฐานข้อมูลที่มีร้านเดียวเป็นหลัก ยังไม่ได้ทดสอบกรณีมีร้านจำนวนมากพร้อมกันซึ่ง RLS Policy จะต้องกรองข้อมูลจากชุดที่ใหญ่กว่า
3. การทดสอบการทำงานพร้อมกันใช้ 20 กระบวนการ ซึ่งสูงกว่าการใช้งานจริงของร้านอาหารขนาดเล็กมาก แต่ยังไม่ใช่การทดสอบรับภาระ (Load Test) ที่ต่อเนื่องเป็นเวลานาน
4. ยังไม่ได้ทดสอบประสิทธิภาพเมื่อตาราง `audit_logs` สะสมข้อมูลครบ 1 ปีก่อนถูก `purge_old_audit_logs()` ลบ

## 8. ขอบเขตที่ยกไปเวอร์ชันถัดไป

| รายการ | เหตุผลที่ยังไม่ทำ |
|---|---|
| การแยกชำระ (Split Bill) | โครงสร้างปัจจุบันรองรับหลายใบสั่งอาหารชำระรวมกันได้แล้ว แต่ไม่รองรับใบสั่งอาหารเดียวแยกชำระหลายส่วน การรองรับต้องเปลี่ยนระดับการอ้างอิงจากใบสั่งอาหารเป็นรายการสั่งอาหาร ซึ่งกระทบโครงสร้างมาก |
| การรวมโต๊ะ | ลูกค้าที่นั่งสองโต๊ะติดกันสามารถชำระรวมได้อยู่แล้วผ่าน `payment_attempt_orders` สิ่งที่ยังไม่รองรับคือการแสดงเป็นใบเดียวบนจอครัว |
| การคืนเงิน | ยังไม่มีตารางรองรับ หากเกิดขึ้นต้องจัดการนอกระบบ |
| การปัดเศษยอดสุทธิ | คอลัมน์ `rounding_adjustment` มีอยู่แล้วแต่ถูกบังคับเป็น 0 ด้วย CHECK Constraint ดูหัวข้อ 3.10 |
| จำนวนลูกค้าต่อโต๊ะ | ใช้สำหรับคำนวณยอดขายเฉลี่ยต่อคน ซึ่งยังไม่จำเป็นในเวอร์ชันแรก |
| การกำหนดว่าใครตั้งรหัส PIN | เป็นประเด็นระดับ API ไม่กระทบโครงสร้างฐานข้อมูล ตัดสินใจภายหลังได้ |

## 9. สิ่งที่ต้องดำเนินการฝั่งแอปพลิเคชัน

ฐานข้อมูลที่ออกแบบไว้จะทำงานได้ตามที่ตั้งใจก็ต่อเมื่อฝั่ง NestJS ดำเนินการต่อไปนี้

1. **เปลี่ยน Database Role เป็น `pos_app`** และเปลี่ยนรหัสผ่านจากค่าตั้งต้น `CHANGE_ME_NOW`
2. **สร้าง Interceptor ที่กำหนด Session Context ทุก Request** หากไม่ทำ ทุกคำสั่งค้นข้อมูลจะคืนผลลัพธ์ว่างเปล่า
3. **ปิด `synchronize` ของ TypeORM** มิฉะนั้นจะลบ Trigger และคอลัมน์ที่สร้างไว้ทิ้ง
4. **ขั้นตอนสมัครร้านต้องสร้าง UUID ฝั่งแอปพลิเคชันก่อน** แล้วกำหนด Session Context ก่อนบันทึก เนื่องจาก RLS ต้องทราบรหัสร้านก่อนการเขียน
5. **ขั้นตอนเข้าสู่ระบบต้องค้นหาผู้ใช้แบบไม่สนตัวพิมพ์** ผ่าน `resolve_user_by_email()`
6. **ตั้งเวลาเรียก `escalate_overdue_shifts()`** ทุก 15 นาที และ `purge_old_audit_logs()` วันละครั้ง
7. **สร้าง `kitchen_ticket_id` หนึ่งค่าต่อการกดส่งครัวหนึ่งครั้ง**
8. **ซิงค์ข้อมูลออฟไลน์** ให้อุปกรณ์สร้าง UUID เองแล้วใช้ `INSERT ... ON CONFLICT DO NOTHING`
9. **ตั้งค่าการสำรองข้อมูลแบบ Point-in-Time Recovery** และทดสอบการกู้คืนอย่างน้อยหนึ่งครั้งก่อนเปิดใช้งานจริง
