# Outbox — ส่วนที่ 1: แนวคิดและการออกแบบ

> เอกสารนี้ยังไม่มีโค้ด · **การตัดสินใจยืนยันแล้วในหัวข้อ 8** · ส่วนที่ 2 จะเป็นโค้ดพร้อมคอมเมนต์ทีละบรรทัด
> ข้อมูลอ้างอิงจากโค้ดจริงใน `main` (`orders.service.ts`, `orders.repository.ts`, `MainPOS.tsx`)

---

## 1. Outbox คืออะไร

**Outbox = กล่องจดหมายขาออกในเครื่อง** ทุกคำสั่งที่ต้องส่งไป server ให้ "หย่อนลงกล่อง" ก่อน แล้วมีคนคอย "ไปส่ง" ทีละฉบับเมื่อไปถึง server ได้

```
พนักงานกด "ส่งครัว"
        │
        ▼
 ┌─────────────┐   flush (ส่งทีละรายการ)   ┌────────┐
 │   outbox    │ ───────────────────────► │ server │
 │ (IndexedDB) │ ◄── สำเร็จ = ลบออกจากกล่อง  └────────┘
 └─────────────┘
   ออฟไลน์ = ค้างในกล่อง รอรอบถัดไป
```

เหมือนพนักงานเสิร์ฟเขียนออเดอร์ลงกระดาษแล้วเสียบไว้ที่ราวหน้าครัว — ครัวยังไม่ว่างก็ไม่หาย ว่างเมื่อไหร่ก็หยิบไปทำตามลำดับ

ระบบจริงที่ใช้แนวคิดนี้: Square POS / Loyverse (ขายออฟไลน์แล้ว sync), Linear และ Figma (เขียนลงเครื่องก่อนแล้วค่อยส่ง), และในฝั่ง backend มีชื่อเรียกว่า "Transactional Outbox Pattern"

---

## 2. ทำไมให้ "ทุกออเดอร์" ผ่าน outbox (ทั้งออนไลน์และออฟไลน์)

ตกลงกันไว้แล้ว ทวนเหตุผล:

| | 2 ทาง (ออนไลน์ยิงตรง / ออฟไลน์เข้าคิว) | **ทางเดียวผ่าน outbox** |
|---|---|---|
| เน็ตหลุด **ระหว่าง** ยิง request | ไม่รู้ว่าเข้า server หรือยัง → ข้อมูลหาย หรือกดซ้ำได้บิลซ้อน | อยู่ในกล่องจนกว่า server ตอบสำเร็จ · ส่งซ้ำได้เพราะ idempotent |
| โค้ด | 2 ชุด | 1 ชุด |
| ทดสอบ | ทางออฟไลน์ถูกใช้นาน ๆ ครั้ง บั๊กซ่อน | ทางเดียวกันถูกใช้ทุกออเดอร์ทุกวัน |

ตอนออนไลน์ผู้ใช้ไม่รู้สึกต่าง — หย่อนลงกล่องแล้ว flush ทันที ใช้เวลาเท่ายิงตรง

---

## 3. ทำไมส่งซ้ำได้โดยไม่เกิดบิลซ้อน (idempotency)

ยืนยันจากโค้ด backend แล้ว:

| คำสั่ง | id มาจาก | server ทำอะไรเมื่อได้รับซ้ำ |
|---|---|---|
| `POST /orders` | `orderId` client สร้าง (`crypto.randomUUID()`) | `ON CONFLICT (order_id) DO NOTHING` → service อ่านบิลเดิมคืน **200** |
| `POST /orders/:id/items` | `orderItemId` ต่อจาน + `kitchenTicketId` ต่อรอบ | `ON CONFLICT (order_item_id) DO NOTHING` → ข้ามจานที่มีแล้ว |

ดังนั้น **กฎเหล็ก: สร้าง UUID ตอนหย่อนลงกล่อง ไม่ใช่ตอนส่ง** — ส่งกี่รอบก็ใช้ id เดิม server จึงรู้ว่าเป็นรายการเดิม

และทุก request อยู่ใน transaction เดียว (`DbContextService` เปิด `BEGIN`/`COMMIT` ต่อ request) → add items 5 จานแล้วจานที่ 3 พัง = rollback ทั้ง 5 ไม่ค้างครึ่ง ๆ

## 4. โครงสร้างข้อมูล

### 4.1 ตารางใหม่ใน Dexie (`db.ts` → `version(2)`)

```
outbox: '++seq, tenantSlug, orderId, status'
```

- `++seq` = เลขรันอัตโนมัติ 1, 2, 3, … → **ลำดับการส่ง** (มาก่อนส่งก่อน)
- index `tenantSlug`, `orderId`, `status` = ไว้ค้นหา/นับ/จัดกลุ่ม
- `snapshots` คงเดิม — เพิ่ม `version(2)` ต่อท้าย **ห้ามแก้ `version(1)`** · Dexie อัปเกรด DB ในเครื่องผู้ใช้ให้เอง ไม่หายข้อมูลเดิม

### 4.2 หน้าตา 1 รายการ

```ts
interface OutboxEntry {
  seq?: number                          // Dexie ใส่ให้
  tenantSlug: string                    // ร้าน
  userId: string                        // คนที่กด (ใช้ในเครื่องเท่านั้น ไม่ส่งขึ้น server)
  kind: 'createOrder' | 'addItems'
  orderId: string                       // ใช้จัดกลุ่ม: รายการของบิลเดียวกันต้องเรียงกัน
  payload: CreateOrderBody | AddItemsBody   // body ที่จะส่ง (มี UUID ครบแล้ว)
  shiftId: string | null                // กะตอนกด (จาก snapshot currentShift) — เผื่อ SHIFT_MISMATCH
  status: 'pending' | 'failed'
  attempts: number                      // ส่งไปกี่รอบแล้ว
  lastError: string | null              // ข้อความ error ล่าสุด (แสดงให้พนักงาน)
  createdAt: number
}
```

### 4.3 กด "ส่งครัว" 1 ครั้ง = หย่อนกี่ฉบับ

ตาม flow เดิมใน `MainPOS.tsx`:

| สถานการณ์ | ฉบับที่หย่อน |
|---|---|
| โต๊ะว่าง (บิลใหม่) | ① `createOrder {orderId, tableId}` → ② `addItems {orderId, items[], kitchenTicketId}` |
| โต๊ะมีบิลอยู่แล้ว | ② `addItems` อย่างเดียว |

ทำไมไม่รวมเป็นฉบับเดียว: `POST /orders` รับ `items` ได้ แต่ **ไม่รับ `kitchenTicketId`** → จานจะเป็น `draft` ไม่เข้าครัว · ใช้ 2 endpoint ตามที่ `MainPOS` ทำอยู่แล้วจึงตรงกับ backend ที่สุด

## 5. การส่ง (flush) — กติกา

### 5.1 ลำดับ

```
1. ล็อก (Web Locks) — แท็บอื่นกำลังส่งอยู่ → รอบนี้ข้าม
2. ดึงรายการ pending ของร้านนี้ เรียงตาม seq
3. วนทีละรายการ:
     ถ้ารายการนี้ไม่ใช่ของ user ที่ login อยู่ → ข้าม (รอเจ้าของ login)
     ถ้าบิลนี้มีรายการ failed อยู่แล้ว      → ข้าม (บิลนี้ติด)
     ส่ง → ดูผล (ตาราง 5.2)
4. ปลดล็อก
```

### 5.2 ผลของการส่ง

| ผล | ตัวอย่าง | ทำอะไร |
|---|---|---|
| **2xx** | 200 / 201 | ลบออกจาก outbox · ไปรายการถัดไป |
| **ติดต่อไม่ได้** | TypeError, 5xx | **หยุดทั้งรอบ** (รายการหลังจากนี้ก็ไปไม่ถึงเหมือนกัน) · `attempts + 1` · รอรอบหน้า |
| **401** | session หมด | `appClient` ลอง refresh ให้ก่อนแล้ว · ถ้ายังได้ 401 = ต้อง login ใหม่ → **หยุดทั้งรอบ เก็บของไว้** |
| **4xx อื่น** | 409 โต๊ะมีบิลแล้ว, 409 เมนูหมด, 409 ไม่มีกะเปิด, 400 | `status = 'failed'` + เก็บ `lastError` · **บิลนี้หยุด บิลอื่นไปต่อ** |

### 5.3 ทำไมต้อง "จัดกลุ่มตามบิล" (ปัญหา poison message)

```
outbox: [1] A1 createOrder   [2] A1 addItems   [3] B2 addItems   [4] A1 addItems
```

ถ้า [1] ล้มด้วย 409 "โต๊ะมีบิลแล้ว":
- **ไม่จัดกลุ่ม แต่หยุดทั้งคิว** → B2 ไม่ได้ส่งด้วย ทั้งที่ไม่เกี่ยว (คิวตายทั้งเส้น)
- **ไม่จัดกลุ่ม และข้ามไปต่อ** → [2] ส่ง addItems ไปบิลที่ไม่มีอยู่ → 404 → พังเป็นทอด ๆ
- **จัดกลุ่ม** ✅ → [1] failed → [2], [4] ข้าม (บิล A1 ติด) → [3] ส่งตามปกติ

### 5.4 เมื่อไหร่จะ flush

| ทริกเกอร์ | เหตุผล |
|---|---|
| หลังหย่อนลงกล่อง | ออนไลน์อยู่ → ส่งทันที ผู้ใช้ไม่รู้สึกช้า |
| `connectionStatus` เปลี่ยนเป็น `online` | เน็ตกลับมา → ส่งของค้าง (ต่อกับ OfflineBanner ที่ทำแล้ว) |
| เปิดแอป / login สำเร็จ | ของค้างจากรอบก่อน |
| ทุก 30 วินาที **เฉพาะตอนมีของค้าง** | กันพลาดกรณีที่ไม่มี event |

ไม่ใช้ Background Sync API — Safari ไม่รองรับ และต้องเขียน service worker เอง

### 5.5 Web Locks — กันส่งซ้อนกันหลายแท็บ

```ts
navigator.locks.request('pwa-pos-outbox', { ifAvailable: true }, async (lock) => {
  if (!lock) return      // แท็บอื่นถือล็อกอยู่ → ไม่ต้องทำ
  // ... flush
})
```

ไม่มีล็อก: 2 แท็บดึงรายการเดียวกัน ส่งพร้อมกัน — server ไม่ซ้อน (idempotent) แต่ทั้งคู่จะลบ/แก้แถวเดียวกันใน Dexie ชนกันเอง

## 7. ความเสี่ยงที่ยังเหลือ (รู้แล้วยอมรับ หรือต้องตัดสิน)

| ความเสี่ยง | ตอนนี้ | ทางแก้ |
|---|---|---|
| ปิดกะจาก **เครื่องอื่น** ระหว่างเครื่องนี้มีของค้าง แล้วเปิดกะวันใหม่ → ออเดอร์ไหลเข้าวันใหม่เงียบ ๆ | กันได้แค่เครื่องตัวเอง | backend `SHIFT_MISMATCH` (เก็บ `shiftId` ไว้ในแต่ละรายการแล้ว รอ backend) — **เบนซ์ขอตัดสินเรื่องนี้ภายหลัง** |
| 409 "โต๊ะมีบิลแล้ว" → อาหารไม่ถึงครัว | ขึ้นในรายการ failed | ดูข้อ 8.2 |
| เมนูหมดระหว่างออฟไลน์ → 409 ทั้งรอบ (transaction rollback ทุกจาน) | ขึ้นในรายการ failed | ดูข้อ 8.2 |
| `/orders/sync` ยังเปิดอยู่ (รับ `any`, `createdBy` จาก body) | outbox **ไม่ใช้** endpoint นี้ | ลบทิ้ง — รอตกลงกับเพื่อน |
| ล้างข้อมูลเว็บ / Incognito → outbox หาย | ข้อจำกัดของ browser | `navigator.storage.persist()` ทำแล้ว · บอกในคู่มือร้าน |

## 8. การตัดสินใจ (confirm แล้ว 2026-10-30)

| # | เรื่อง | ตัดสิน | ผลต่อการเขียนโค้ด |
|---|---|---|---|
| A | อ่าน outbox ใน React | **`dexie-react-hooks` (`useLiveQuery`)** | ลง package เพิ่ม 1 ตัว · component re-render เองเมื่อ outbox เปลี่ยน ไม่ต้องเขียน store เอง |
| B | รายการที่ส่งไม่สำเร็จ (failed) | **แบบ (2): ดู + ลบ + ส่งใหม่** | ปุ่ม "ลองส่งอีกครั้ง" เปลี่ยน `failed` กลับเป็น `pending` แล้ว flush · "รวมเข้าบิลเดิม" เลื่อนเป็น V2 (โดเมน Order ของเพื่อน) |
| C | logout ตอนมีของค้าง | **บล็อก** | outbox ของ user นี้ไม่ว่าง (ทั้ง `pending` และ `failed`) → กด logout ไม่ได้ + แจ้ง "มี X รายการยังไม่ส่ง" · logout ลบ snapshot แต่ **ไม่ลบ outbox** |
| D | หน้าทดสอบ | **ใส่เฉพาะตอน dev** | route `/:tenantSlug/dev/outbox` ลงทะเบียนเมื่อ `import.meta.env.DEV` เป็น true เท่านั้น · `npm run build` จะไม่มีหน้านี้ |

### 8.1 โครงไฟล์ที่ยืนยันแล้ว

```
features/offline/
  db.ts                          แก้   version(2) เพิ่มตาราง outbox
  outbox.ts                      ใหม่  enqueue / retry / discard / นับจำนวน
  flush.ts                       ใหม่  flushOutbox() + startOutboxRunner()
  hooks/useOutbox.ts             ใหม่  useLiveQuery: จำนวนรอส่ง/ล้ม + รายการ failed
  components/OfflineBanner.tsx   แก้   แสดง "รอส่ง X รายการ" / "ส่งไม่สำเร็จ X รายการ"
  components/FailedOutbox.tsx    ใหม่  รายการที่ส่งไม่สำเร็จ + ปุ่มลองส่งอีกครั้ง / ลบ
  pages/OutboxDevPage.tsx        ใหม่  หน้าทดสอบ (เฉพาะ dev)
features/auth/hooks/useLogin.ts  แก้   บล็อก logout ถ้า outbox ไม่ว่าง
features/offline/components/UpdatePrompt.tsx   แก้   ซ่อน "อัปเดตเลย" ถ้า outbox ไม่ว่าง
routes/AppRouter.tsx             แก้   route dev (มีเงื่อนไข import.meta.env.DEV)
main.tsx                         แก้   startOutboxRunner()
```

**ไม่แตะ** `MainPOS.tsx`, `KDSContext.tsx`, `orders.*` ของเพื่อน — การต่อสายเข้าหน้า POS และปุ่มปิดกะเป็นขั้นถัดไป

### 8.2 จุดที่ต้องระวังจากการตัดสินใจ

- **C (บล็อก logout)**: ถ้ามีรายการ `failed` ค้าง พนักงานต้องกด "ลองส่งอีกครั้ง" หรือ "ลบ" ก่อนจึงจะออกได้ — ต้องมีลิงก์จากข้อความบล็อกไปที่รายการ failed ไม่งั้นพนักงานจะติดอยู่โดยไม่รู้ว่าต้องทำอะไร
- **C (บล็อก logout) + session หมดอายุ**: session หมดเองไม่ผ่านปุ่ม logout → ไม่ถูกบล็อก · outbox ยังอยู่ รอ user เดิม login แล้วส่งต่อ (ตามกฎ userId ในข้อ 5.1)
- **D (เฉพาะ dev)**: ใช้ `import.meta.env.DEV` ที่ Vite แทนค่าเป็น `true`/`false` ตอน build → โค้ดหน้าทดสอบถูกตัดทิ้งจาก bundle จริง (tree-shaking) ไม่ใช่แค่ซ่อน
