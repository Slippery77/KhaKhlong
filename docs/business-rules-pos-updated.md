# เอกสารกฎเกณฑ์ทางธุรกิจ (Business Rules)
## PWA-POS: ระบบจุดขายสำหรับธุรกิจร้านอาหารขนาดเล็ก

> **สถานะเอกสาร (อัปเดตล่าสุด รอบ 12):** ครอบคลุม 10 โมดูล — Order/Order Item, Payment, Inventory, Void vs Comp, Table Management, Menu Management + Modifier, Kitchen Display System, Shift & Cash Reconciliation, Receipt System, Audit Log, System Configuration, และ User/Employee Management
>
> **หมายเหตุการแก้ไขรอบ 12 (ทดสอบประสิทธิภาพและความถูกต้องของการตั้งค่า):** ทดสอบประสิทธิภาพและ Concurrency บนข้อมูลจริง 90 วัน ผ่านทั้งหมด (ดูหัวข้อ 16) และพบว่าการตั้งค่า `rounding_mode` ไม่มี Trigger หรือฟังก์ชันใดอ่านไปใช้เลย จึงเป็นการตั้งค่าที่แสดงบนหน้าจอว่าตั้งได้แต่ไม่มีผลจริง **การตั้งค่านี้ถูกลบออก** เหลือ 9 รายการ และคอลัมน์ `payments.rounding_adjustment` ถูกบังคับเป็น 0 ด้วย CHECK Constraint (ดู `CFG-09`)
>
> **หมายเหตุการแก้ไขรอบ 11 (Schema Hardening — ก่อนขึ้นใช้งานจริง):** ทบทวนการออกแบบทั้งระบบด้วยการรันทดสอบบน PostgreSQL 16.13 จริง พบข้อบกพร่องที่ต้องแก้ 6 ประการและช่องโหว่เชิงออกแบบ 11 ประการ จำนวนตารางเปลี่ยนจาก 23 เป็น **28 ตาราง** และเพิ่ม 3 View กฎที่เปลี่ยนแปลงในรอบนี้ ได้แก่ `ORD-04` (Void ตอน `preparing` ได้แล้ว), `ORD-10` ถึง `ORD-12` (ใหม่), `PAY-03` (เปลี่ยนเป็น Configurable), `PAY-10` ถึง `PAY-12` (ใหม่), `INV-03` (ปรับ Enum), `INV-12` (ใหม่), `SHIFT-11` (**กลับมติเดิม** — เพิ่ม `opened_by`), `SHIFT-12` ถึง `SHIFT-14` (ใหม่), `MENU-05` (ใหม่), `CFG-06` ถึง `CFG-08` (ใหม่), `AUD-07` (ใหม่), `USR-06` (ใหม่) — ดูรายละเอียดเหตุผลเชิงเทคนิคที่ `claude/database-design-revision.md` และโครงสร้างจริงที่ `FULL_INSTALL.sql`
>
> **หมายเหตุรอบ 10 (Architectural Change):** เปลี่ยนสถาปัตยกรรม Inventory จาก Recipe-based Real-time Deduction เป็น Periodic Physical Count (`INV-11`) ยกเลิก `ORD-03`, `ORD-07`, `MOD-04`, `MOD-05`, `INV-04` ถึง `INV-06` และลบตาราง `menu_item_recipes`, `modifier_recipes`
>
> เอกสารนี้เป็นผลจากการวิเคราะห์ร่วมกันระหว่างผู้จัดทำโครงงานและ AI Assistant โดยยึดเอกสาร Scope และ Role Permission Matrix เป็นฐาน

## 1. หลักการสถาปัตยกรรมร่วม (Architectural Invariants)

| ID | หลักการ | เหตุผล |
|---|---|---|
| INV-01 | **Immutable Payment** — Record ในตาราง `payments` ห้ามมีการ UPDATE หรือ DELETE หลังถูกสร้างแล้วเด็ดขาด | รักษาความถูกต้องของข้อมูลทางการเงินสำหรับการกระทบยอดและตรวจสอบภายหลัง **[รอบ 11]** เดิมบังคับใช้ด้วย Permission เพียงชั้นเดียว ปัจจุบันบังคับ 3 ชั้น ได้แก่ Permission `payment:edit_closed` ที่ไม่มอบให้ใคร, Trigger `immutable` ที่ปฏิเสธทุก UPDATE/DELETE และ `REVOKE UPDATE, DELETE` ที่ระดับ Database Role |
| INV-02 | **Append-only Ledger** — การเปลี่ยนแปลงที่มีผลทางการเงินและสต็อกบันทึกเป็น Record ใหม่เสมอ ไม่ UPDATE ค่าเดิม | ตารางที่ใช้หลักนี้ ได้แก่ `inventory_transactions`, `receipt_print_logs`, `audit_logs` และ **[รอบ 11]** `cash_movements` ที่เพิ่มใหม่ |
| INV-12 **[เพิ่มรอบ 11]** | **Tenant Isolation ต้องบังคับทั้งการอ่านและการเขียน** — Foreign Key ทุกจุดที่ข้ามตารางใช้ Composite Key ที่รวม `tenant_id` | การทดสอบพบว่า RLS ควบคุมการอ่านข้ามร้านได้ แต่ไม่ควบคุมการเขียน Foreign Key ที่ชี้ไปแถวของร้านอื่น ทำให้สร้าง Order ของร้าน A ผูกโต๊ะของร้าน B ได้สำเร็จ การใช้ Composite FK ปิดช่องนี้ที่ระดับ Referential Integrity ซึ่งเป็นแนวทางที่ Citus แนะนำสำหรับ Multi-tenant Schema |

## 2. Order & Order Item Lifecycle

### 2.1 สถานะของ Order Item

```
draft ──(ส่งเข้าครัว)──> queued ──(ครัวเริ่มทำ)──> preparing ──(ทำเสร็จ)──> ready ──(เสิร์ฟ)──> served
  │                         │                          │
  │ (ยกเลิก)                │ (ยกเลิก)                 │ (ยกเลิก + ต้องมี void:approve)
  ▼                         ▼                          ▼
voided                   voided                     voided
```

หลังสถานะ `served` ไม่ใช้ Void แต่ใช้กลไก Comp แทน (ดู `ORD-05`)

| ID | กฎ | เหตุผล |
|---|---|---|
| ORD-01 | สถานะติดตามในระดับ **Order Item** ไม่ใช่ระดับ Order ทั้งใบ | โต๊ะเดียวกันอาจมีรายการที่ครัวเริ่มทำแล้วและยังไม่เริ่มทำพร้อมกัน จำเป็นต้องแยก Granularity เพื่อรองรับ `ORD-04` |
| ORD-02 | "พักออเดอร์" (`draft`) เก็บลง IndexedDB (Local-first) ก่อน Sync ขึ้น Server เมื่อมีการเชื่อมต่อ | ป้องกันข้อมูลสูญหายหากอุปกรณ์ขัดข้อง และรองรับการทำงานหลายอุปกรณ์พร้อมกัน |
| ~~ORD-03~~ | **[ยกเลิกรอบ 10]** ไม่มีการตัดสต็อกอัตโนมัติจาก Order อีกต่อไป | Inventory เปลี่ยนเป็น Periodic Physical Count (ดู `INV-11`) |
| ORD-04 **[แก้ไขรอบ 11]** | Void ทำได้ที่สถานะ `queued` และ **`preparing`** โดยการ Void ขณะ `preparing` ต้องมีสิทธิ์ `void:approve` และระบุเหตุผลเสมอ ส่วนสถานะ `served` ขึ้นไปใช้ Comp แทน | เดิมอนุญาตเฉพาะ `queued` ทำให้กรณีลูกค้าขอยกเลิกขณะครัวกำลังทำ พนักงานต้องรอจนทำเสร็จ เสิร์ฟออกไป แล้วค่อย Comp ซึ่งไม่ตรงกับหน้างานจริง การแยกระดับสิทธิ์ทำให้ยังคงควบคุมความเสี่ยงไว้ได้ เพราะการยกเลิกของที่ครัวลงมือทำแล้วมีต้นทุนวัตถุดิบเกิดขึ้นจริง ฐานข้อมูลบังคับสิทธิ์นี้ซ้ำใน Trigger `trg_order_item_state()` |
| ORD-05 | หลังสถานะเป็น `served` แล้ว **ห้าม Void** โดยเด็ดขาด ใช้กลไก **Comp** แทน | ป้องกัน Void Fraud (เสิร์ฟอาหารจริงแล้วยกเลิกทิ้งเพื่อไม่เก็บเงิน) ซึ่งเป็นช่องโหว่ทุจริตที่พบบ่อยในธุรกิจร้านอาหาร |
| ORD-06 | Permission `cancel:approve` ถูกตัดออก การยกเลิกทั้งออเดอร์ทำได้โดยสั่ง Void ทีละ Order Item ด้วยกลไกเดิม | ป้องกันความสับสนระหว่าง 2 Permission ที่ทำหน้าที่ซ้ำซ้อนกัน สอดคล้องกับแนวทางที่ Toast และ Square ใช้จริง |
| ~~ORD-07~~ | **[ยกเลิกรอบ 10]** ไม่มีการเช็คสต็อกตอนสั่งอาหาร | ดู `INV-11` |
| ORD-08 | **1 Order Item = 1 หน่วยเสมอ ไม่มี Field `quantity`** สั่งเมนูเดียวกันหลายจานสร้างเป็นหลายแถวแยกกัน | ขยายหลักการ Granularity เดียวกับ `ORD-01` มาถึงระดับการ Void/Comp — ถ้าลูกค้าขอยกเลิกแค่ 1 ใน 3 จาน การมี 1 แถวต่อ 1 จานทำให้ UPDATE แถวเดียวจบ **[รอบ 11]** Trade-off เรื่องจำนวนแถวแก้ที่ชั้นแสดงผลด้วย View `v_receipt_lines` ซึ่งจัดกลุ่มตามราคาและชุด Modifier ไม่ใช่ตามเมนูอย่างเดียว เพื่อไม่ให้จานที่เพิ่ม Topping ถูกรวมกับจานธรรมดา |
| ORD-09 | `orders.table_id` เป็น NOT NULL ทุก Order ต้องผูกกับโต๊ะเสมอ | ตรงตาม Scope Doc ที่ระบุว่า Takeaway/Delivery เป็น Phase 2 — **หมายเหตุความเสี่ยง:** การเพิ่ม Takeaway ในอนาคตเป็น Breaking Change |
| **ORD-10 [เพิ่มรอบ 11]** | `orders` เพิ่ม Field `order_number` (เลขจำนวนเต็ม รันใหม่ทุกวันทำการ) แยกจาก `order_id` ที่เป็น UUID | `order_id` เป็น UUID ซึ่งพนักงานเรียกกันปากเปล่าไม่ได้ การเปลี่ยน Primary Key เป็นเลขรันถูกพิจารณาแล้วและปฏิเสธด้วย 4 เหตุผล: (1) เลขรันตามวันที่ชนกันระหว่างร้าน (2) ขัดกับการทำงานแบบออฟไลน์ เพราะเลขรันต้องสอบถามฐานข้อมูลก่อนจึงจะรู้ค่าถัดไป ขณะที่ UUID อุปกรณ์สร้างเองได้แล้ว Sync ภายหลัง ซึ่งเป็นเหตุผลหลักของการเลือกสถาปัตยกรรม PWA (3) เลขรันคาดเดาได้ ทำให้ไล่ดูบิลของคนอื่นในร้านเดียวกันผ่าน API ได้ (4) กระทบ Foreign Key ทุกตาราง — แนวทางสองชั้นนี้เป็นแนวทางเดียวกับที่ Shopify ใช้ (`id` กับ `name`) และ Stripe ใช้ (`in_1A2b...` กับ `invoice_number`) |
| **ORD-11 [เพิ่มรอบ 11]** | `orders` เพิ่ม Field `closed_at`, `closed_by`, `close_reason` โดย `close_reason` รับค่า `paid`, `voided_all`, `empty`, `walkout` การปิดบิลโดยไม่เก็บเงินต้องมีสิทธิ์ `order:close_unpaid` | เดิมสถานะการปิดบิลอนุมานจาก `payment_id IS NOT NULL` เพียงอย่างเดียว ทำให้กรณีลูกค้าเดินออกไปโดยไม่สั่ง ลูกค้าเบี้ยวบิล หรือรายการถูกยกเลิกทั้งหมด บิลจะค้างตลอดไปและโต๊ะไม่กลับมาว่าง ระบบเขียน Audit Log ประเภท `order_closed_unpaid` อัตโนมัติทุกครั้งที่ปิดด้วยเหตุผลที่ไม่ใช่ `paid` |
| **ORD-12 [เพิ่มรอบ 11]** | ห้ามเปิดบิลใหม่หากไม่มีกะที่สถานะ `open` ของวันทำการนั้น | เป็นคู่กับ `PAY-12` เพื่อให้ยอดขายทุกบาทผูกกับกะเสมอ ดูเหตุผลเต็มที่ `PAY-12` |

## 3. Payment

| ID | กฎ | เหตุผล |
|---|---|---|
| PAY-01 | ความสัมพันธ์ระหว่าง Payment และ Order เป็น **1 Payment : N Order** | Order ของแต่ละโต๊ะยังคงเป็น Record แยกกัน ไม่มีการหลอมรวมข้อมูล เพื่อคง Traceability |
| PAY-02 | Bill Merge อนุญาตเฉพาะกรณีลูกค้ากลุ่มเดียวกันที่นั่งแยกโต๊ะ | จำกัดขอบเขตให้ตรงกับสถานการณ์จริง ลดความเสี่ยงการใช้ฟีเจอร์นี้เพื่อซ่อนรายการ |
| PAY-03 **[แก้ไขรอบ 11]** | เงื่อนไขก่อนชำระเงิน: Order Item ทุกรายการต้องมีสถานะ `served` ครบถ้วน — **เปลี่ยนจาก Hard Rule เป็น Configurable** ผ่าน `require_all_served_before_payment` (ค่าเริ่มต้น `true`) | กฎเดิมเป็น Strict Policy ที่ไม่มีข้อยกเว้น ทำให้ร้านที่จ่ายก่อนกิน ร้านชาบูบุฟเฟต์ และกรณีพนักงานลืมกดเสิร์ฟ ชำระเงินไม่ได้เลย การเปลี่ยนเป็น Configuration ทำให้ร้านที่ต้องการความเข้มงวดยังคงได้พฤติกรรมเดิม ขณะที่ร้านรูปแบบอื่นปรับได้เองโดยไม่ต้องแก้โค้ด |
| PAY-04 | VAT คำนวณที่ระดับ **Payment (Transaction Level)** เท่านั้น โดยรวม Subtotal ทุกโต๊ะก่อนแล้วคำนวณครั้งเดียว | ป้องกัน Rounding Error สะสมจากการคำนวณแยกแต่ละ Order |
| PAY-05 | Payment แบ่งเป็น 2 ตาราง: `payment_attempts` (Mutable) และ `payments` (Immutable) | รองรับลักษณะ Asynchronous ของ QR Payment, รองรับ Idempotency ป้องกันการหักเงินซ้ำ และคง Audit Trail ของรายการที่ล้มเหลว |
| PAY-06 | หากการชำระเงินล้มเหลว ทุกโต๊ะที่ถูกเลือกมารวมบิลต้องกลับสู่สถานะเดิมทั้งหมด (Atomic) | ป้องกัน Partial State **[รอบ 11]** บังคับใช้ด้วย Field `payment_attempt_orders.is_open` ที่ถูกปิดอัตโนมัติเมื่อ Attempt เปลี่ยนเป็น `failed` หรือ `timeout` พร้อม Partial Unique Index ที่รับประกันว่า 1 บิลมี Attempt ค้างได้ครั้งละอันเดียว ป้องกันการจ่ายซ้ำจากสองเครื่องพร้อมกัน **[รอบ 12]** ทดสอบด้วยสองกระบวนการพร้อมกันจริงแล้ว ดูหัวข้อ 16.2 |
| PAY-07 | `business_date` คำนวณจาก Trading Day Cutoff ตาม `business_day_start_hour` คำนวณครั้งเดียวตอน Insert แล้ว Freeze | รองรับร้านที่เปิดข้ามเที่ยงคืน **[รอบ 11]** ฐานข้อมูลคำนวณค่านี้ให้เองผ่านฟังก์ชัน `compute_business_date()` ซึ่งคิดตาม Timezone ของแต่ละร้าน ไม่ให้แอปพลิเคชันส่งค่ามาเอง |
| PAY-08 | `payment_attempt_orders` เป็น Junction Table บันทึกว่า Attempt หนึ่งพยายามจ่ายให้ Order ใดบ้าง | รองรับ `PAY-06` อย่างสมบูรณ์ — ถ้าไม่ Persist ความสัมพันธ์นี้ ระบบจะไม่รู้ว่าต้อง Revert โต๊ะไหนกรณี Server Restart ระหว่างรอ Webhook |
| PAY-09 | `payments.payment_method` เก็บซ้ำจาก `payment_attempts` โดยเจตนา | ให้ `payments` เป็น Self-sufficient สำหรับ Generate ใบเสร็จและ Query Report โดยไม่ต้อง JOIN ย้อนกลับ **[รอบ 11]** Trigger ตรวจสอบว่าค่าทั้งสองตรงกันทุกครั้งที่สร้าง Payment จึงไม่มีโอกาสเพี้ยน |
| **PAY-10 [เพิ่มรอบ 11]** | ระบบรองรับภาษีมูลค่าเพิ่ม 3 โหมดผ่าน Config `vat_mode` ได้แก่ `none` (ค่าเริ่มต้น), `inclusive`, `exclusive` และบันทึก `vat_mode`, `vat_rate_snapshot`, `service_charge_rate_snapshot` ไว้ในทุกรายการชำระเงิน | **ค่าเริ่มต้นเป็น `none`** เพราะร้านอาหารขนาดเล็กจำนวนมากไม่ได้จดทะเบียนภาษีมูลค่าเพิ่ม หากตั้งค่าเริ่มต้นเป็นโหมดที่มีภาษี ร้านเหล่านี้จะออกเอกสารที่มีรายการภาษีโดยไม่ตั้งใจ ซึ่งเป็นความผิดพลาดที่ร้ายแรงกว่าการไม่ออก — **โหมด `inclusive`** หมายถึงราคาเมนูที่เจ้าของร้านกรอกคือราคาที่ลูกค้าจ่ายจริง ระบบแกะภาษีออกมาแสดงด้วยสูตร `vat = ROUND(total − total/(1+rate/100), 2)` แล้วหา `subtotal = total − vat − service − rounding` การคำนวณในลำดับนี้ทำให้ตัวเลขบนเอกสารบวกกันได้เท่ากับยอดรวมเสมอ หากคำนวณภาษีแยกแล้วนำมาบวกจะเกิดผลต่าง 1 สตางค์ในบางยอด (**[รอบ 12]** `rounding` ในสูตรเป็น 0 เสมอ ดู `CFG-09`) — **การเก็บ Snapshot** ทำให้พิมพ์เอกสารย้อนหลังได้ถูกต้องแม้อัตราภาษีจะเปลี่ยนไปแล้ว ซึ่งขยายหลักการเดียวกับ `MOD-06` และ `CFG-01` |
| **PAY-11 [เพิ่มรอบ 11]** | เลขที่ใบเสร็จและเลขที่บิลออกจากตาราง Counter แยก (`receipt_sequences`, `order_sequences`) ด้วยคำสั่ง `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` | การหาเลขถัดไปด้วย `MAX() + 1` เกิด Race Condition เมื่อมีการชำระเงินพร้อมกันจากสองเครื่อง ทำให้ละเมิด Unique Constraint และรายการล้มเหลว การใช้ตาราง Counter กับคำสั่ง Upsert เป็นการดำเนินการแบบ Atomic ภายในคำสั่งเดียว **[รอบ 12]** ทดสอบด้วยการชำระเงินพร้อมกัน 20 รายการแล้วได้เลขเรียงต่อเนื่องไม่ซ้ำและไม่ข้าม ดูหัวข้อ 16.2 |
| **PAY-12 [เพิ่มรอบ 11]** | ห้ามบันทึกการชำระเงินหากไม่มีกะที่สถานะ `open` ของวันทำการนั้น และยอดของ `payment_attempts` อนุญาตให้เป็น 0 ได้ | **เหตุผลข้อแรก** หากไม่บังคับ กฎ "ปิดกะเท่ากับปิดร้าน" จะอยู่แค่ในเอกสาร เมื่อพนักงานปิดกะแล้วมีลูกค้าเข้ามาอีก เงินที่รับจะไม่เข้ากะใดเลยและยอดกระทบไม่ตรงโดยไม่มีใครรู้ **เหตุผลข้อที่สอง** `CHECK (amount > 0)` เดิมทำให้บิลที่ถูก Comp ครบทุกรายการ (ยอด 0 บาท) ปิดไม่ได้เลย |

## 5. Void vs. Comp (Complimentary)

| หัวข้อ | Void | Comp |
|---|---|---|
| ใช้เมื่อสถานะ **[แก้ไขรอบ 11]** | `queued` หรือ `preparing` | `served` เท่านั้น |
| สิทธิ์ที่ต้องมี **[แก้ไขรอบ 11]** | `queued` ไม่ต้องอนุมัติ · `preparing` ต้องมี `void:approve` | `discount:approve` |
| ผลต่อ Inventory | ไม่มีผล (ดู `INV-11`) | ไม่มีผล |
| ผลต่อ Order Item | ไม่นับในบิล | ยังอยู่ในบิล แต่ราคาเป็น 0 ทั้งรายการรวม Modifier |
| Field ที่เกี่ยวข้อง | `voided_by`, `voided_at`, `void_reason` | `is_comped`, `comp_reason`, `comped_by`, `comped_at` |

| ID | กฎ | เหตุผล |

## 9. Shift & Cash Reconciliation

### 9.1 สถานะของ Shift

```
open ──(ปิดกะ variance = 0)──> closed_auto
  │
  └──(ปิดกะ variance ≠ 0)──> pending_verification ──(Manager รับรอง)──> verified
                                   │
                                   └──(เกินเวลา)──> escalated ──(Owner รับรอง)──> verified

closed_auto / pending_verification ──(reopen_shift โดย Manager/Owner)──> open
verified / escalated ──> ปิดตาย เปิดใหม่ไม่ได้
```

### 9.2 Business Rules

| ID | กฎ | เหตุผล |
|---|---|---|
| SHIFT-01 | Shift ผูกกับรอบวันขายของร้าน (`business_date`) ไม่ผูกกับพนักงานรายคน 1 วันมี 1 Shift | สอดคล้องกับการใช้ Cash Drawer เดียวร่วมกันทั้งร้าน **[รอบ 11]** `business_date` ไม่ให้กรอกเอง ระบบคำนวณจาก `compute_business_date()` เดียวกับที่ใช้ใน `PAY-07` ทำให้ไม่มีโอกาสที่วันของกะกับวันของการชำระเงินจะเหลื่อมกัน |
| SHIFT-02 | `expected_closing_cash` คำนวณอัตโนมัติ ไม่ใช่ค่าที่กรอกด้วยมือ | ลดความผิดพลาดจากการคำนวณมือ **[รอบ 11]** สูตรขยายเป็น `opening_cash + ยอดขายเงินสด + เงินเข้าลิ้นชัก − เงินออกจากลิ้นชัก` ตาม `SHIFT-13` |
| SHIFT-03 | หาก `variance = 0` ระบบปิด Shift อัตโนมัติ ไม่ต้องรอ Manager | ลดภาระงานธุรการเมื่อไม่มีความผิดปกติ Manager เข้ามาเฉพาะกรณีที่ต้องตรวจสอบจริง |
| SHIFT-04 | หาก `variance ≠ 0` สถานะเปลี่ยนเป็น `pending_verification` | เงินขาดหรือเกินคือสัญญาณผิดปกติที่ต้องมีการตรวจสอบก่อนปิดยอดอย่างเป็นทางการ |
| SHIFT-05 | ระยะเวลารอ Manager ก่อน Escalate เป็นค่า Configurable | รองรับความแตกต่างของแต่ละร้านโดยไม่ต้องแก้โค้ด |
| SHIFT-06 | หากเกินเวลาแล้ว Manager ยังไม่ Verify ระบบเปลี่ยนเป็น `escalated` และมอบหมายให้ Owner | ป้องกันรายการค้างตรวจสอบไม่มีที่สิ้นสุด **[รอบ 11]** ดำเนินการด้วยฟังก์ชัน `escalate_overdue_shifts()` ที่ตั้งเวลาเรียกทุก 15 นาที |
| SHIFT-07 | Shift ที่ค้างตรวจสอบไม่ Block การเปิด Shift ของวันถัดไป | ธุรกิจร้านอาหารต้องดำเนินต่อได้ทุกวัน ไม่ควรถูกงานธุรการ Block การขาย |
| SHIFT-08 | Cash Drawer เดียวใช้ร่วมกัน Variance คำนวณที่ระดับ Shift เท่านั้น ไม่สืบระดับรายบุคคล | Trade-off ที่ยอมรับโดยตั้งใจ เหมาะกับร้านที่มีพนักงานน้อยคน ลดความซับซ้อนของระบบ |
| SHIFT-09 | `payments.processed_by` ยังคงบันทึกทุกธุรกรรมเพื่อ Audit พื้นฐาน แม้ไม่ใช้เป็นฐานคำนวณ Variance | รักษา Audit Trail ระดับ Transaction ไว้ |
| SHIFT-10 | `shifts` มี Field `closed_at` คู่กับ `closed_by` | จำเป็นต่อการคำนวณ `SHIFT-05` ซึ่งต้องนับจากเวลาที่ปิดกะ ไม่ใช่เวลาที่เปิดกะ |
| SHIFT-11 **[กลับมติเดิมในรอบ 11]** | `shifts` **มี** Field `opened_by` (NOT NULL) และ `opened_at` | **มติรอบ 9 ระบุว่าไม่ต้องมี Field นี้** โดยให้เหตุผลว่าสอดคล้องกับ `SHIFT-08` ที่ไม่ต้องการ Individual Accountability ของ Cash Drawer — การทบทวนรอบ 11 พบว่าเหตุผลนั้นสับสนระหว่าง 2 เรื่อง `SHIFT-08` พูดถึงการสืบว่า **ใครทำให้เงินขาด** ซึ่งสืบไม่ได้จริงเพราะลิ้นชักใช้ร่วมกัน แต่ `opened_by` ตอบคำถามคนละข้อคือ **ใครเป็นผู้เปิดกะและกรอกยอดเงินตั้งต้น** ซึ่งเป็นการกระทำของคนคนเดียวในเวลาเดียว สืบได้ชัดเจน และเป็นตัวเลขตั้งต้นของการกระทบยอดทั้งวัน นอกจากนี้ระบบมี Permission `shift:open` อยู่แล้ว การมีสิทธิ์โดยไม่บันทึกว่าใครใช้สิทธิ์นั้นขัดกับหลักที่ใช้กับทุก Permission อื่นในระบบ |
| **SHIFT-12 [เพิ่มรอบ 11]** | Manager หรือ Owner เปิดกะที่ปิดไปแล้วใหม่ได้ผ่านฟังก์ชัน `reopen_shift()` ซึ่งต้องมีสิทธิ์ `shift:reopen` และระบุเหตุผลเสมอ เปิดได้เฉพาะกะที่สถานะ `closed_auto` หรือ `pending_verification` **ไม่อนุญาต** สำหรับ `verified` และ `escalated` | **ปัญหาที่ต้องแก้** `SHIFT-01` กำหนด 1 กะต่อวัน และ `ORD-12`/`PAY-12` ห้ามขายเมื่อไม่มีกะเปิด ทั้งสามข้อรวมกันทำให้การกดปิดกะผิดระหว่างวันเท่ากับร้านขายของไม่ได้อีกเลยทั้งวัน — **ข้อจำกัดที่ตั้งใจ** กะที่ผ่านการรับรองแล้วถือเป็นหลักฐานทางบัญชีที่ปิดแล้ว การเปิดใหม่จะขัดกับหลัก Immutable เช่นเดียวกับ `INV-01` — **การล้างค่า** ระบบล้าง `actual_closing_cash`, `expected_closing_cash`, `closed_at`, `closed_by` แต่ **คงยอดเงินเปิดกะเดิมไว้** เพื่อไม่ให้แก้ยอดตั้งต้นให้ตรงกับที่นับได้ภายหลัง พร้อมเพิ่มตัวนับ `reopen_count` และเขียน Audit Log ประเภท `shift_reopened` ที่บันทึกสถานะเดิมและยอดเดิมไว้ใน Metadata — **เหตุผลที่ไม่สร้างตาราง Log แยก** `audit_logs` มี `tenant_id`, `user_id`, `ip_address`, `device_info` และ `metadata` ครบอยู่แล้ว การสร้างตารางแยกจะได้บันทึกที่ขาดบริบทเมื่อเทียบกับบันทึกอื่น และทำให้หน้า Audit Log ต้องอ่านจากสองแหล่ง |
| **SHIFT-13 [เพิ่มรอบ 11]** | ตาราง `cash_movements` บันทึกเงินเข้าและออกจากลิ้นชักที่ไม่ใช่การขาย ต้องมีสิทธิ์ `cash:movement` ซึ่งไม่มอบให้พนักงาน | หากไม่มีตารางนี้ ยอดเงินสดที่ระบบคาดหวังจะคำนวณจากยอดขายเงินสดบวกเงินเปิดกะเท่านั้น เมื่อพนักงานหยิบเงินไปซื้อน้ำแข็งหรือแลกธนบัตรย่อย ยอดที่นับได้จะไม่ตรงทุกวัน ทำให้กลไกการกระทบยอดสูญเสียความหมาย เพราะมีส่วนต่างเป็นเรื่องปกติจนไม่มีใครสนใจตรวจสอบ — **เหตุผลที่จำกัดสิทธิ์** การบันทึกเงินออกส่งผลโดยตรงต่อ `expected_closing_cash` หากพนักงานบันทึกเองได้ จะสร้างรายการเงินออกปลอมเพื่อกลบส่วนต่างที่ตนเองทำให้เกิดขึ้นได้ — ตารางนี้เป็น Append-only ตาม `INV-02` |
| **SHIFT-14 [เพิ่มรอบ 11]** | สิทธิ์ `shift:open`, `shift:close_and_count`, `shift:verify` ถูกตรวจสอบซ้ำในฐานข้อมูลผ่าน Trigger | เป็นการใช้หลัก Defense-in-Depth — ชั้น Application ป้องกันการเข้าถึงผ่าน API ตามปกติ แต่ไม่ครอบคลุมกรณีที่ Guard ถูกกำหนดผิดพลาดใน Endpoint ใด Endpoint หนึ่ง |

## 11. Audit Log

### 11.1 หลักการออกแบบ: Hybrid Logging

ระบบ POS อุตสาหกรรมใช้แนวทาง **Risk-based Logging** คือบันทึกเฉพาะ Action ที่กระทบเงิน สต็อก หรือสิทธิ์ ไม่บันทึกทุก HTTP Request เพราะข้อมูลจะเยอะเกินจำเป็นและไม่มีประโยชน์เชิงตรวจสอบ

หลายอย่างในระบบนี้มี Ledger ของตัวเองอยู่แล้ว (`inventory_transactions`, `payment_attempts`, `receipt_print_logs`, Field `is_comped`) จึงไม่ต้องบันทึกซ้ำอีกชั้นในตาราง `audit_logs` เพื่อป้องกัน Data Inconsistency ระหว่าง 2 แหล่งที่เก็บเรื่องเดียวกัน

### 11.2 Action ที่บันทึกในตาราง `audit_logs`

**[รอบ 11]** ขยายจาก 7 เป็น 17 ประเภท

| กลุ่ม | Action |
|---|---|
| การเข้าใช้ระบบ | `login_success` · `login_failed` · `logout` |
| บัญชีผู้ใช้ | `user_created` · `user_deactivated` · `user_reactivated` · `role_changed` · `pin_changed` · `password_changed` · `pin_locked` |
| การตั้งค่า | `config_updated` · `menu_price_updated` · `table_status_changed` · `tenant_updated` |
| รายการเสี่ยง | `order_closed_unpaid` · `shift_reopened` · `inventory_adjusted` |

### 11.3 Business Rules

| ID | กฎ | เหตุผล |
|---|---|---|
| AUD-01 | สร้าง Record ใน `audit_logs` เฉพาะ Action ที่ไม่มี Ledger ของตัวเองอยู่แล้ว | ป้องกัน Data Duplication และ Inconsistency ระหว่าง 2 แหล่งข้อมูล |
| AUD-02 | บันทึก `ip_address` และ `device_info` ทุกครั้ง | รองรับ Security Audit ข้อมูลนี้ถือเป็นข้อมูลส่วนบุคคลตาม PDPA จึงต้องมี Retention Policy กำกับชัดเจน |
| AUD-03 | เก็บ `audit_logs` ไว้ 1 ปีแล้วลบทิ้ง | ครอบคลุมรอบปีบัญชี ต้นทุนพื้นที่จัดเก็บต่ำมาก **[รอบ 11]** บังคับด้วย Trigger ที่อนุญาตให้ลบได้เฉพาะแถวอายุเกิน 1 ปี ผ่านฟังก์ชัน `purge_old_audit_logs()` ที่ตั้งเวลาเรียกวันละครั้ง จึงไม่มีทางลบ Log ใหม่ทิ้งโดยตั้งใจหรือพลาด |
| AUD-04 | Index ที่ `created_at`, `user_id`, `action_type` ตั้งแต่เริ่มสร้างตาราง | ป้องกัน Query ช้าเมื่อข้อมูลสะสมมากขึ้น |
| AUD-05 | สิทธิ์เข้าถึงหน้า Audit Log จำกัดเฉพาะ Owner และ Manager ผ่าน `audit_log:view` | สอดคล้องกับ Pattern เดิมที่ให้สิทธิ์ตรวจสอบรายการอ่อนไหวแก่ 2 Role นี้ |
| AUD-06 | `audit_logs` มี Field `tenant_id` (NOT NULL) และ `user_id` เป็น Nullable | ถ้าไม่มี `tenant_id` ตารางนี้จะเป็นตารางเดียวในระบบที่ไม่มี Tenant Isolation ส่วน `user_id` ต้อง Nullable เพราะกรณี Login ล้มเหลวด้วย Username ที่ไม่มีอยู่จริงจะไม่มี User ให้ผูก |
| **AUD-07 [เพิ่มรอบ 11]** | Audit Log ถูกเขียนโดย **Trigger ในฐานข้อมูล** ไม่ใช่โดย Application ยกเว้น 3 Action ที่เกี่ยวกับการเข้าใช้ระบบ | การพึ่งให้ Application เขียน Audit Log เองมีจุดอ่อนที่หากผู้พัฒนาลืมเขียนใน Endpoint ใด Endpoint หนึ่ง การกระทำนั้นจะไม่ถูกบันทึกเลยและไม่มีใครรู้ การย้ายไปเขียนที่ Trigger ทำให้ไม่มีทางที่ข้อมูลจะเปลี่ยนโดยไม่ถูกบันทึก ไม่ว่าจะเข้าถึงผ่านช่องทางใด — ส่วน `login_success`, `login_failed`, `logout` ยังเขียนจากฝั่ง Application เพราะเป็นเหตุการณ์ที่เกิดนอกขอบเขตของ Transaction ที่แตะตารางใด |

| USR-04 | ความสัมพันธ์ User-Role เป็น Many-to-One ผ่าน `role_id` ไม่รองรับ Multi-role | เรียบง่ายพอสำหรับร้านอาหารขนาดเล็กที่แต่ละคนมีบทบาทชัดเจน |
| USR-05 | `username` Unique เฉพาะภายใน `tenant_id` ไม่ใช่ Unique ข้ามแพลตฟอร์ม | ร้าน A และร้าน B ใช้ Username ซ้ำกันได้โดยไม่ขัดแย้ง **[รอบ 11]** เปลี่ยนเป็น Unique แบบไม่สนตัวพิมพ์ เพราะเดิม `Admin` กับ `admin` ถูกมองเป็นคนละบัญชี ซึ่งเปิดช่องให้สร้างบัญชีที่ดูเหมือนกันเพื่อหลอกผู้ใช้ ข้อเดียวกันใช้กับ Email ด้วย |
| **USR-06 [เพิ่มรอบ 11]** | `users` เพิ่ม Field สำหรับความปลอดภัย 5 รายการ ได้แก่ `password_failed_attempts`, `password_locked_until`, `pin_failed_attempts`, `pin_locked_until` และ `token_version` พร้อมตาราง `refresh_tokens` | **เหตุผลเรื่อง PIN** รหัส PIN มีความยาว 4 ถึง 6 หลัก หากฐานข้อมูลรั่วไหลจะถูกถอดรหัสได้ในเวลาไม่นานแม้เก็บเป็น Hash และหากไม่จำกัดจำนวนครั้งที่ลองผิด ผู้ที่เข้าถึงเครื่องได้สามารถเดา PIN ของ Manager เพื่ออนุมัติ Void และ Comp เองได้ ซึ่งทำให้กลไก Re-authentication ตาม `COMP-02` ไร้ความหมาย — **เหตุผลเรื่อง Token** `USR-02` ระบุว่า User ที่ถูกปิดใช้งาน Login ไม่ได้อีก แต่ JWT เป็น Stateless เมื่อออก Token ไปแล้วจะใช้ได้จนหมดอายุแม้บัญชีจะถูกปิดไปแล้ว `token_version` ที่ขยับค่าทำให้ Token เก่าใช้ไม่ได้ทันที ส่วน `refresh_tokens` ทำให้เพิกถอน Session รายอุปกรณ์ได้ |

## 16. ผลการทดสอบประสิทธิภาพและ Concurrency

**[เพิ่มรอบ 12]** ทดสอบบน PostgreSQL 16.13 ด้วยข้อมูลจำลองร้านขนาดจริง 40 โต๊ะ 60 เมนู ย้อนหลัง 90 วัน รวม 7,200 บิล 28,800 รายการอาหาร และ 7,200 รายการชำระเงิน ขนาดฐานข้อมูล 29 MB

### 16.1 เวลาตอบสนองของแต่ละการทำงาน

| การทำงาน | เวลา |
|---|---|
| เปิดบิล 1 ใบ | 5.7 ms |
| สั่งอาหาร 4 รายการ | 2.1 ms |
| เปลี่ยนสถานะในครัว 1 ขั้น | 0.5–1.4 ms |
| Query ของจอครัว | 0.27 ms |
| บันทึกการชำระเงิน | 5.8 ms |
| รายงานยอดขายรายวัน 90 วัน | 2.7 ms |
| รายงานเมนูขายดี 90 วัน | 9.1 ms |
| ค้นใบเสร็จย้อนหลัง 30 วัน | 0.6 ms |

**ต้นทุนของ Trigger** วัดด้วยวงจรเต็ม 200 รอบ (เปิดบิล สั่ง 4 จาน ส่งครัว ยกเลิก และปิดบิล) โดยเปรียบเทียบระหว่างเปิดและปิด Trigger

| | เวลารวม | ต่อรอบ |
|---|---|---|
| Trigger ทำงาน | 398.6 ms | 1.99 ms |
| Trigger ปิด | 140.9 ms | 0.70 ms |
| ส่วนต่าง | | 1.29 ms |

Trigger ทำให้ช้าลงประมาณ 2.8 เท่า แต่คิดเป็น 1.3 มิลลิวินาทีต่อบิล ร้านที่ขาย 200 บิลต่อวันเสียเวลารวม 0.26 วินาทีทั้งวัน ซึ่งเป็นต้นทุนที่ยอมรับได้เมื่อแลกกับการบังคับกฎที่ข้ามไม่ได้ทุกกรณีตาม `SHIFT-14` และ `AUD-07`

### 16.2 ผลการทดสอบ Concurrency

ทดสอบด้วยกระบวนการแยกที่ทำงานพร้อมกันจริง ไม่ใช่การจำลองในคำสั่งเดียว

| สถานการณ์ | ผล |
|---|---|
| สองเครื่องกดชำระบิลเดียวกันพร้อมกัน | เครื่องหนึ่งสำเร็จ อีกเครื่องถูกปฏิเสธด้วย Unique Constraint เหลือ Attempt เดียวตาม `PAY-06` |
| สองเครื่องบันทึกการชำระจาก Attempt เดียวกัน | เครื่องหนึ่งสำเร็จ อีกเครื่องถูกปฏิเสธ เหลือ Payment เดียว |
| ยี่สิบเครื่องชำระยี่สิบบิลพร้อมกัน | สำเร็จครบ 20 รายการ ได้เลขที่ใบเสร็จไม่ซ้ำ 20 เลข เรียงต่อเนื่องไม่ข้าม ยืนยัน `PAY-11` |

### 16.3 ข้อจำกัดของการทดสอบ

- ทดสอบบนเครื่องจำลอง ไม่ใช่เครื่องที่จะใช้งานจริง ตัวเลขเวลาจะต่างออกไป
- วัดเฉพาะเวลาที่ฐานข้อมูลใช้ ไม่รวมเวลาเครือข่ายและการประมวลผลฝั่ง NestJS
- ข้อมูลย้อนหลังสร้างโดยปิด Trigger ชั่วคราว ฐานข้อมูลจริงจะมี `audit_logs` สะสมมากกว่านี้
- ยังไม่ได้ทดสอบเมื่อ `audit_logs` สะสมถึงหลักล้านแถว ซึ่งจะเกิดขึ้นเมื่อใช้งานครบ 1 ปี
